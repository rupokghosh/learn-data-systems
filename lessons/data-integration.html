Data integration

Every earlier chapter ended with some version of "it depends". B-trees or LSM-trees, leaders or quorums, batch or streams: each tool is good at some access patterns and poor at others. A real application rarely has only one access pattern, so it rarely gets away with only one tool. The interesting engineering question is no longer which database to pick, but how to keep several of them telling the same story.

One write, many shapes

Picture a city bike-sharing service. Riders start and end rentals in an app. The same facts are needed in many shapes: a search box that finds stations with free bikes, a cache that answers "where is bike B-112?" in a millisecond, a warehouse where analysts compute average ride length, a model that tells the operations team where to send a van, and a service that emails a receipt when a ride ends. No single product is good at all five.

The way out is to be strict about which copy is the truth. A system of record holds the authoritative version of each fact, written once, normalized. Everything else is derived data: a search index, cache, aggregate, or model that you could throw away and recompute from the system of recordderived data: Redundant by design. Losing it costs time, not information.. That distinction is not a property of any product. PostgreSQL can be a system of record in one design and a derived read model in another. What matters is the direction of the dataflow.

Write once, in order, and derive the rest

The tempting way to feed five systems is to have the application write to all five. These dual writes fail in two ways. If the process crashes between the third and fourth write, the systems disagree permanently. Worse, two concurrent requests can reach the database in one order and the search index in the other, so each system ends up with a different last value, and nothing will ever notice.

The fix is to funnel all writes through a single place that decides their order, then let every other system follow that order. The change log of the database, exposed through change data captureDebezium reads the PostgreSQL and MySQL replication logs and publishes each committed change to Kafka. Many teams instead write events to Kafka first and let the database be one of the consumers., or an event log written to first, gives each consumer the same sequence. Because each derived system is a deterministic function of that sequence, every one of them converges to the same answer. They may be stale, as the warehouse in the figure is for seconds at a time, but they never contradict each other once caught up.

Total order has limits. A single log is a single leader, and its throughput caps the whole system, so large deployments partition it, and events in different partitions have no defined order. Data centres in different regions usually each keep their own leader, so two regions can order the same pair of events differently. Microservices that each own their state have no shared log at all. And an order derived from arrival time can still violate causality: if a rider reports a bike broken and a mechanic then marks it fixed, a consumer that sees those on two unrelated partitions may process the fix first. Common mitigations are routing related events by the same key, giving events unique identifiers that later events can reference, or, where order cannot be guaranteed, designing the derived state so that application order does not matter.

Derived data or distributed transactions

Distributed transactions, such as two-phase commit across a database and a search engine, offer a different way to keep copies in step. They give linearizable reads: once the write commits, every system shows it. Log-based derivation gives asynchronous updates and eventual consistency, with no ability to read your own write in the index right away unless you build for it. In exchange it tolerates a slow or broken consumer without blocking writes, and it can be replayed. In practice XA transactions are rarely supported well across heterogeneous systems, and a fault anywhere amplifies into unavailability everywhere. For integrating different kinds of storage, a log with idempotent, deterministic consumers is usually the more robust choice, even though it asks you to think about staleness.

Reprocessing to evolve an application

Derived views are not frozen. Suppose the station search should now hide bikes that are flagged for repair. You cannot patch the existing index, because it never tracked flags. With the log retained, you can start a second version of the index that replays history from offset 0 with the new logic, while the first version keeps answering queries. When the new one has caught up, you shift reads to it, perhaps a few percent of users at a time, and retire the old one only when you are confident. Every step is reversible until the last one.

This is the same idea as a gradual schema migration, minus the riskiest part: the system of record is not rewritten in place. It works only if you keep enough history, which is why Kafka topics that feed derived views are often configured with long retention or log compaction, and why batch jobs over the full history in a data lake remain valuable even when everything else is streaming.

Batch and stream together

Replaying history is batch processing; following new writes is stream processing. For a while, a popular design ran both side by side: the lambda architecture recorded immutable events, a stream processor produced a fast approximate view, and a batch job later produced a corrected view that replaced it.

Its weaknesses were practical. The same logic had to be written twice, in two frameworks, and kept equivalent. Merging the two outputs at read time was its own source of bugs. And the batch layer often had to reprocess everything each time, because incremental batch processing is hard. Modern engines such as Apache Flink, and Spark's structured streaming, close the gap by running one job over both the replayed history and the live tail. That needs three things: replaying the log from any offset, exactly-once semantics for state and output, and windowing by event time rather than processing time, so that a replay of last month gives the same result as last month's live run.
