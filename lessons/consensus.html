Fault-tolerant consensus

Consensus means getting several nodes to agree on something. It sounds modest, yet it is one of the most important and most subtle problems in distributed systems. Electing one leader for a database, so that two nodes never both accept writes, is consensus. Deciding whether a distributed transaction commits, so that no node commits while another aborts, is consensus. Fixing the order of messages in total order broadcast is consensus, repeated for every message.

The problem, stated precisely

In the formal version, one or more nodes propose values and the algorithm decides on one of them. A correct algorithm satisfies four properties:

  • Uniform agreement: no two nodes decide differently.
  • Integrity: no node decides twice.
  • Validity: a decided value was proposed by some node.Validity rules out trivial algorithms, such as one that always decides "null" whatever was proposed.
  • Termination: every node that does not crash eventually decides.

The first three are safety properties, and on their own they are easy: appoint one node as dictator and let it decide everything. Termination is what makes the problem hard, because the algorithm must keep deciding when nodes fail, the dictator included. Two-phase commit fails this test: if its coordinator dies, the participants wait indefinitely. A consensus algorithm tolerates the crash of any minority of its nodes. A cluster of five keeps deciding with two nodes down.

There is a famous negative result. In 1985, Fischer, Lynch, and Paterson proved that in a fully asynchronous system, with no clocks or timeouts and messages that may take any amount of time, no deterministic algorithm can guarantee consensus if even one node might crash. Practical algorithms get around it by using timeouts to suspect crashed nodes, or randomness. When a timeout fires wrongly, safety is never at risk; the algorithm may only stall until the network calms down. Every consensus system makes this deal: always correct, and live when the network is reasonable.

Epochs, leaders, and overlapping quorums

Raft, Multi-Paxos, Zab, and Viewstamped Replication do not decide one value at a time from scratch. They implement total order broadcast directly: a leader proposes the next entry in a log, and the group votes on it. That looks circular, since choosing a leader is itself consensus. The way out is an epoch number, called a term in Raft, a ballot number in Paxos, an epoch in Zab, and a view in Viewstamped Replication.

Within one epoch there is at most one leader. When nodes suspect that the leader has died, one of them starts an election for a higher epoch, and each node votes for at most one candidate per epoch. If two nodes both think they lead, in different epochs, the higher epoch wins.

A leader cannot simply trust that it still leads, since a newer epoch may have started behind its back. So every proposal is a second vote. The leader sends the entry to the others and waits for a quorum, usually a majority, to accept it, and a node accepts only if it has not seen a higher epoch. Any two majorities of the same cluster share at least one node, so the quorum that accepts a proposal overlaps the quorum that elected any newer leader. If a newer epoch exists, at least one voter knows about it, refuses, and tells the old leader that it has been replaced.

The grey ring around each follower is its election timeout running down, randomized so that nodes rarely expire together. When one runs out, that node becomes a candidate (orange), increments its term, and sends RequestVote to everyone. A node grants its vote only if it has not voted in that term and the candidate's log is at least as up to date as its own. The first candidate to collect three votes leads the term and sends AppendEntries, both as a heartbeat and to replicate commands. Send a few commands and watch the log table: an entry turns green once the leader knows a majority stores it.In Raft the commit index lives in memory, so a node you restart shows nothing committed until the leader's next heartbeat tells it.

Now isolate the leader with one follower. The old leader still accepts commands, but it reaches only two of five nodes, so those entries never commit. On the other side, three nodes time out, elect a new leader in a higher term, and commit normally. Heal the partition: the old leader sees the higher term, steps down, and its uncommitted entries are overwritten by the new leader's log. Two nodes may each believe they lead for a while, but never in the same term, and the stats line checks that every committed entry is identical on every node.

What consensus costs

  • Every write is a vote. A proposal is acknowledged only after a majority has stored it, which is synchronous replication. Many databases use asynchronous replication precisely to avoid that latency, and accept that a failover can lose recent writes.
  • A strict majority must be reachable. Three nodes tolerate one failure, five tolerate two. During a partition the minority side cannot make progress, as the simulation shows.
  • Membership is usually fixed. Raft has an extension for adding and removing nodes, but it is markedly harder to get right than the core algorithm.
  • Failure detection relies on timeouts. Where network delays vary widely, false suspicions trigger elections, and while an election runs nothing commits. A node with a flaky link can keep starting elections and disrupt a healthy leader, which is why many implementations add a pre-vote round. Keep the election timeout well above normal round trips; etcd's defaults are a 100 ms heartbeat and a 1 s election timeout.

Coordination services

Few applications implement consensus themselves. They use a coordination service such as ZooKeeper or etcd. These hold a small amount of data, small enough to fit in memory, replicated across three or five nodes by a consensus algorithm, and offer a handful of features that are easy to build on:

  • Linearizable atomic operations. A compare-and-set is enough for a lock or a lease: when several nodes try to create the same key, exactly one succeeds.
  • Total ordering of operations. Every change gets a number that only grows, the zxid in ZooKeeper and the revision in etcd. That number makes a good fencing token (Chapter 8): storage can reject a write from a lock holder whose token is older than one it has already seen.
  • Failure detection. Clients hold a session (ZooKeeper) or a lease (etcd), kept alive by heartbeats. When the heartbeats stop, the service expires it and deletes the keys tied to it, which releases any locks that client held.
  • Change notifications. Clients can watch keys and are told when they change, so a node learns that a lock was released or a peer joined without polling.

The typical uses follow from those features. Allocating work: when exactly one node should run a job, or partitions must be assigned to nodes and reassigned when one dies, the coordination service holds the decision. Kafka used ZooKeeper for this for years before moving to its own Raft-based controller quorum, and Kubernetes keeps all of its cluster state in etcd. Service discovery: finding the current address of the payment service. This rarely needs consensus, since a slightly stale answer is usually fine, but it is convenient to keep next to everything else. Membership: agreeing which nodes are currently considered alive, a consensus decision about a fact that is inherently uncertain.

A practical rule: keep slow-changing coordination state in the service, such as who leads, who owns which partition, and configuration, and keep the application's data elsewhere. A coordination service is built for small, rarely changing data, not for your order table. That split lets an application run on thousands of nodes while only three or five of them take part in consensus.
