Partitioning and secondary indexes

Partitioning by primary key works because every lookup names the key, and the key alone says where the record lives. Real applications also ask questions by other attributes: every listing in Lisbon, every order containing a given product, every message that mentions a word. Answering those quickly needs a secondary index, the bread and butter of relational databases and the entire reason search engines exist.

Secondary indexes do not fit neatly onto partitions. The primary key decides where a record is stored, and the indexed value has nothing to do with that decision. Take a holiday rental site whose listings are partitioned by listing ID, with guests filtering by city. Listings in Lisbon can be on any partition, so the index has to be split up somehow too. There are two broad ways to do it.

Local indexes: one per partition

In the first approach, each partition keeps its own secondary index covering only the listings it holds. Adding, changing, or removing a listing touches only the partition that owns its ID: the document and its index entries change in one local write, which can be atomic. Because the index is split the same way as the documents, this is called a document-partitioned or local index.

The cost lands on reads. A listing's ID says nothing about its city, so a query by city has to be sent to every partition and the partial results combined. This pattern is called scatter/gather. Each partition does a small, cheap lookup, but the query as a whole waits for the slowest reply. If one partition in a hundred happens to be in a garbage collection pause or busy with compaction, a query that fans out to fifty partitions meets at least one such straggler about 40 percent of the time.1 − 0.9950 ≈ 0.39. The more partitions a read must wait for, the more its latency is set by the slowest of them.

Local indexes are the common default. Elasticsearch sends a search to one copy of every shard and merges the best hits from each. Cassandra's built-in secondary indexes and MongoDB's indexes on a sharded collection are also local to each partition. The practical defence against scatter/gather is to choose a partition key that your most frequent queries include. If nearly every search on the rental site is within one city, partitioning listings by city turns those searches into single-partition reads and leaves fan-out for the rare query that spans cities.

Global indexes: partitioned by term

The alternative is one index that covers every listing, partitioned separately from the listings. Entries for cities from A to J might live on partition 0, cities starting with K on partition 1, and so on. The index is split by the value being looked up, which search engines call a term, so this is a term-partitioned or global index. Splitting terms by range keeps range queries over values such as price efficient; splitting by a hash of the term spreads load more evenly.

Reads become cheap. A query for Lisbon asks the single partition that holds the Lisbon entry. If the entry carries a copy of the fields the query needs, nothing else is contacted. Otherwise the reader fetches each matching listing from its own partition, which is still more targeted than asking everyone.

Writes become expensive. A new listing is stored on the partition that owns its ID, but its index entry belongs to the partition that owns its city, often on another machine. Moving a listing to a different city touches up to three partitions: the listing itself, the entry for the old city, and the entry for the new one. Keeping all of them exactly in step needs a distributed transaction, which most databases avoid for index maintenance. Instead, global index updates are usually asynchronous: the write is acknowledged once the listing is stored, and the index catches up a moment later.

In global mode, change a listing's city and query the new city straight away: the listing is stored, the write was acknowledged, and yet the index does not know about it. That window is what asynchronous maintenance costs. Amazon DynamoDB works this way: its global secondary indexes are updated asynchronously, usually within a fraction of a second, and reads from them are only eventually consistent. Its local secondary indexes live next to the items they cover and support strongly consistent reads. Distributed SQL databases such as CockroachDB and Google Spanner take the other road and update a global index in the same transaction as the row, so index reads are consistent and writes pay for a cross-partition commit.

Choosing between them

Local (by document)Global (by term)
Partitions read per queryAll of themOne, plus any document fetches
Partitions written per changeOneUp to three
Index freshnessUpdated with the data, atomicallyUsually lags the data
Query latency set byThe slowest partitionOne partition
ExamplesElasticsearch, Cassandra, MongoDB, DynamoDB local indexesDynamoDB global indexes; CockroachDB and Spanner, synchronously

Local indexes suit write-heavy data where queries by the secondary attribute are rare, can include the partition key, or can tolerate fan-out. A global index pays off when the secondary lookup is a hot read path, as long as the application can live with a read that briefly misses a fresh write, or the database is willing to pay for a transaction on every write. Either way, every index you add is a cost on writes, and on a partitioned database that cost is measured in machines as well as in disk.
