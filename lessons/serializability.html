Serializability

The previous lessons collected a catalogue of anomalies, each with its own partial fix. Keeping that catalogue in your head while writing every transaction is hard, and static analysis cannot reliably tell you which of your code paths are exposed. Serializable isolation removes the question. It guarantees that the result of running transactions concurrently is the same as running them one at a time, in some order, so any transaction that is correct on its own stays correct under concurrency.

Databases provide this in one of three ways: by actually running one transaction at a time, by two-phase locking, or by optimistic checking as in serializable snapshot isolation.

Actually running one at a time

The most direct approach is to drop concurrency: a single thread executes transactions one after another. For decades this was considered too slow, but two things changed. Memory became cheap enough to hold many working datasets entirely in RAM, so a transaction never waits for disk. And designers noticed that transactions in online systems are usually short and touch few rows. VoltDB, Redis, and Datomic all execute writes serially, and a single thread without locking overhead can sometimes beat a concurrent engine.

The catch is that a transaction must never leave the thread idle. An interactive transaction, where the application sends a query, waits for the answer, thinks, and sends the next, would hold the single thread hostage for network round trips. So serial systems require the whole transaction to be submitted up front as a stored procedure. Stored procedures have a poor reputation, because traditional vendor languages are awkward to test, version, and debug, but VoltDB uses Java and Redis uses Lua, which helps.

Throughput is capped at one CPU core. To go further you partition the data so each partition has its own thread, which works only if most transactions touch a single partition. A transaction that spans partitions needs all of them to coordinate, and runs much slower. Serial execution fits when transactions are short, the active data fits in memory, the write rate fits one core per partition, and cross-partition work is rare.

Two-phase locking

For around thirty years, two-phase locking (2PL) was the main way to get serializability, and it is still what MySQL's InnoDB and SQL Server use at the serializable level. Its rule is stricter than the row locks of read committed: a reader takes a shared lock on everything it reads, and a writer takes an exclusive lock. Several transactions can share a shared lock, but an exclusive lock excludes everyone. A transaction that read a row and now wants to write it upgrades its lock. All locks are held until commit or abort. The two phases are growing, while locks are acquired, and shrinking, when they are all released at the end.

So writers block readers and readers block writers, the opposite of snapshot isolation's promise. Transactions also end up waiting for each other in circles: each holds a lock the other needs. The database watches a wait-for graph, and when it finds a cycle it aborts one transaction so the others can continue. That deadlock is not a bug in your application; it is a normal outcome that the application must handle by retrying.

Locking individual rows is not enough to stop phantoms, because the row that would conflict does not exist yet. A predicate lock locks every object that matches a search condition, including ones inserted later, but checking every write against every active predicate is slow. Real systems approximate it with index-range locks: the transaction locks a range of an index that covers its condition, perhaps more than strictly necessary. Without a suitable index, the database falls back to locking the whole table.InnoDB calls its version next-key locking: it locks an index record and the gap before it.

The cost of 2PL is not only the deadlocks. Waiting is unbounded: one slow transaction holding a lock on a popular row stalls every transaction behind it, and they stall the ones behind them. Even at modest load, response times at high percentiles can be erratic.

Serializable snapshot isolation

Serializable snapshot isolation (SSI), first described in 2008 and available in PostgreSQL since version 9.1, takes the opposite bet. Two-phase locking is pessimistic: if something might go wrong, wait. SSI is optimistic: let every transaction run on its snapshot without blocking, and at commit time check whether something went wrong. If it did, abort.

What goes wrong under snapshot isolation is a decision based on a premise that has since become false: "two guards are on duty" was true in the snapshot but no longer true at commit. SSI tracks two situations in which a premise may be outdated:

  • Stale reads. A transaction read a version while ignoring a newer, uncommitted write by another transaction. If that other transaction commits first, what the reader saw is out of date.
  • Writes that affect earlier reads. A transaction writes data that another, concurrent transaction has already read. SSI records reads much like index-range locks, but these markers never block anyone; they only flag the conflict.

Each case is a read-write conflict between two transactions. One conflict alone is harmless: the reader can be placed before the writer in the serial order. Trouble needs a pivot, a transaction with a conflict coming in and a conflict going out, where the far end has already committed. PostgreSQL looks for this structure and aborts one of the transactions involved, usually the one trying to commit. That rules out every anomaly, at the cost of some aborts that were not strictly necessary.

Because readers never block, SSI handles read-heavy workloads and long read-only queries well. Its weak spot is the opposite of 2PL's: under high contention many transactions do work that is then thrown away and retried, and the retries add load.

Both schemes do well when conflicts are rare and badly when every transaction fights over the same few rows; no algorithm makes a hot row cheap. The difference is in how they fail. Under 2PL, contention shows up as waiting and deadlocks, and readers suffer along with writers. Under SSI, it shows up as aborted work, while read-only transactions sail through. Raise the read-only share and SSI pulls ahead.

In practice: if your transactions are short, your data fits in memory, and you can partition by the key most transactions use, serial execution is simple and fast. If you need a general-purpose database, prefer one that offers serializable snapshot isolation, keep transactions short so the window for conflicts stays small, and write the retry loop once, carefully, for every transaction.
