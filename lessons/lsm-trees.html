SSTables and LSM-trees

The log with a hash index had two weaknesses: every key had to fit in memory, and range queries were impossible. Both come from the same place. The records in each segment sit in the order they were written, so the only way to find anything is to remember exactly where it is.

Change one rule and both problems shrink: keep the log-structured design, with its sequential writes and immutable segments, but require every segment to be sorted by key. That sounds impossible for a structure that only appends, since writes arrive in any order. The trick is to sort in memory first and write to disk only once the data is in order.

Sorted segments

A segment file whose records are sorted by key, with each key appearing at most once per file, is called a Sorted String Table, or SSTableThe names SSTable and memtable come from Google's Bigtable paper (2006). LevelDB and RocksDB inherited them.. Sorting buys three things.

Merging becomes cheap, even for files far larger than memory. Open the input files side by side, repeatedly take the smallest key at the head of any input, and write it to the output. This is the merge step of mergesort. When several inputs hold the same key, keep the version from the newest segment and skip the rest. The output comes out sorted too, written in one sequential pass.

The in-memory index can be sparse. If you know that hel starts at byte 4096 and nbo starts at byte 8192, then lim, if it exists, is somewhere in between. You read that one block and scan it. One index entry per few kilobytes of data is enough, so billions of keys no longer need billions of index entries.

Finally, each block can be compressed before it is written, and the sparse index points at the start of each compressed block. That saves disk space and, just as importantly, I/O bandwidth.

The memtable and the write path

Writes still arrive in random order, so they first go into a sorted structure in memory, the memtable. Any balanced search tree works, such as a red-black tree; LevelDB and RocksDB use a skip list. Inserting into it is cheap, and reading it out in key order is trivial. When the memtable grows past a threshold, typically a few megabytes, it is written to disk as a new SSTable. Because the data is already sorted, that flush is one sequential write. A fresh memtable takes new writes while the old one is being flushed.

Memory does not survive a crash, so every write is also appended to a write-ahead log on disk before it is acknowledged. That log is in arrival order and is never read during normal operation. Its only job is to rebuild the memtable after a restart, and it is deleted as soon as the memtable it protects has been flushed.

A read checks the memtable first, then the newest SSTable, then older ones, and stops at the first version of the key it finds. Background compaction keeps the number of SSTables down by merging them and dropping overwritten values and tombstones.

Put together, this is a log-structured merge-treeLSM-tree: Named in a 1996 paper by Patrick O'Neil and colleagues. Today it is the engine inside LevelDB, RocksDB, Cassandra, HBase, ScyllaDB, and many others.. Lucene, the indexing library behind Elasticsearch and Solr, stores its term dictionary in a similar way, with immutable sorted segment files merged in the background.

Bloom filters: skipping segments

The read path has a weak spot: looking up a key that does not exist. The engine must check the memtable and then every SSTable whose key range might contain it, all the way down to the oldest, before it can say "not found". With dozens of files, that is dozens of disk reads for nothing.

So each SSTable carries a Bloom filter: a small bit array, kept in memory, that answers "could this file contain this key?" To add a key, hash it with several hash functions and set the bit each one points to. To test a key, check those same bits. If any of them is 0, the key was never added, guaranteed. If all are 1, the key is probably there, but other keys may have set those bits by coincidence. That is a false positive, and it costs one wasted read. A filter never produces false negatives.

The false-positive rate depends on how many bits you spend per key. A common setting in LevelDB and RocksDB is 10 bits per key, about a byte and a quarter, which gives roughly a 1% false-positive rate with the best number of hash functions. Because the filters sit in memory, ruling a file out costs no I/O at all. Filters do nothing for range queries, though: a scan has to visit every file whose key range overlaps the range you asked for.

Compaction strategies

When and what to merge is the main tuning knob of an LSM-tree, and two families dominate. Size-tiered compaction waits until there are several SSTables of similar size and merges them into one bigger table. Files grow in tiers, each write is rewritten relatively few times, and writes are cheap. The price is that the same key can sit in many tables at once, so reads may check more files, and a big merge temporarily needs room for both its inputs and its output. Cassandra's long-standing default strategy works this way, and HBase uses a variant of it.

Leveled compaction splits the key range into many small, non-overlapping SSTables per level, with each level about ten times larger than the one above. Compaction moves a few files at a time into the next level, so the work is incremental and disk usage stays close to the live data size. A point read checks at most one table per level below L0. The price is that data is rewritten more often as it sinks through the levels. LevelDB and RocksDB use leveled compaction by default, and Cassandra offers it as an option.

Switch the simulator between the two and write until a few flushes have happened. Size-tiered piles up overlapping tables; leveled keeps lower levels tidy but compacts more often. Either way, writes stay sequential, the data stays sorted for range scans, and the engine can absorb write rates far above what an update-in-place design could handle.
