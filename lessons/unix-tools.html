Batch processing with Unix tools

Most of the systems in the earlier chapters answer questions as they arrive: a request comes in, the database looks something up, a response goes back. A large share of real data work looks nothing like that. Every night a job reads yesterday's orders and rebuilds the recommendations. Every hour a job rolls raw click events into a reporting table. Nobody is waiting on the other end of a socket. The job reads a large, bounded pile of input, grinds through all of it, and writes a pile of output.

That is batch processing, and the best place to start learning it is a terminal, because the tools that ship with every Unix system already embody most of the ideas that Hadoop and Spark later scaled up to thousands of machines.

Services, batch jobs, and streams

It helps to sort data systems by what they are waiting for. An online service waits for a request and is judged by response time and availability; a slow answer is a broken answer. A batch job takes a fixed input, runs for minutes or hours, and is judged by throughput: how much data it gets through per unit of time.Throughput is also why batch jobs are usually scheduled rather than triggered. The user never sees the latency of one record, only whether the report was ready by morning. A stream processor sits between the two: it consumes input as it arrives, like a service, but it does not answer a caller, like a batch job. The next chapter covers streams. This one stays with bounded input.

A log report in one line of shell

Suppose you run the web site for a small bakery and want to know which pages are requested most often. The web server writes one line per request: a timestamp, the client address, the method, the path, the status code, and the time taken. Five standard programs, joined by pipes, answer the question:

cat access.log |
  awk '{print $4}' |   # keep only the path
  sort |               # bring equal paths together
  uniq -c |            # count each run of equal lines
  sort -rn |           # biggest count first
  head -n 5            # top five

Each program reads lines on its standard input and writes lines on its standard output. None of them knows what came before it or what comes after. Walk through the stages below and watch the data change shape.

Try counting client addresses: one address that keeps asking for /wp-login.php and getting 404 is someone scanning for a WordPress install that this site does not have. Changing the question meant changing one argument to awk. The rest of the pipeline did not care.

Hash table or sort?

The same report is easy to write as an ordinary program. Read each line, pull out the path, and bump a counter in a dictionary:

counts = {}
for line in open("access.log"):
    path = line.split()[3]
    counts[path] = counts.get(path, 0) + 1
for path, n in sorted(counts.items(), key=lambda kv: -kv[1])[:5]:
    print(n, path)

For this log, the dictionary version is faster: it reads the file once and never sorts the full list of requests. The difference shows up when the number of distinct keys grows. The hash table must hold every distinct key in memory at once, plus per-entry overhead. The sort-based pipeline never needs that. GNU sort fills a fixed buffer, sorts it, writes it to a temporary file as a sorted run, and repeats; at the end it merges the runs, reading each one sequentially.The buffer size is set with sort -S, and --parallel lets it use several cores. Sorted runs merged from disk are the same trick an LSM-tree uses for its segments. Memory stays flat while the input grows, and the disk is read and written in long sequential passes, which disks are good at.

Neither approach is better in general. If the working set fits in memory, count in memory. If it might not, sort first, because sorting degrades gracefully into disk I/O while a hash table degrades into swapping and then into an out-of-memory kill. Distributed batch systems lean heavily on the sorting side of this trade-off, as the next lesson shows.

Why the pieces compose

The striking thing about the pipeline is that five programs written by different people, decades apart, snap together with no glue code. A few design choices make that work.

One uniform interface. Every program reads and writes a stream of bytes, by convention a sequence of newline-separated text records. Any output can become any input. Compare that with two arbitrary services in a company, which usually need an adapter, a schema negotiation, and a meeting before they can exchange data.

Logic separated from wiring. uniq does not open files or decide where its output goes. The shell connects standard output to the next standard input. The program contains only its logic, so the person composing the pipeline decides the wiring, and can redirect to a file, a network socket, or another program without touching the code.Programs that need several inputs or outputs fit this model less well, which is one reason larger systems added their own job schedulers.

Inputs are never modified. Running the pipeline does not change access.log. You can run it again, compare outputs, and try variations freely. A bad experiment costs nothing.

Transparency. You can stop the pipeline at any stage and look at the intermediate output, exactly as the step-through above does, or pipe a stage into less to see whether it does what you expected. Debugging is reading text.

Where a single machine runs out

The limitation is in the name of the tool: a pipe connects processes on one machine. When the log is ten terabytes spread across a hundred servers, a single sort is bounded by one machine's disks and cores, however clever its buffering. The interesting question is whether the same ideas, uniform files, small programs that do one thing, immutable inputs, and sorting as the workhorse, can be spread across a cluster. MapReduce was the first widely used answer, and it is close to a distributed version of this pipeline.
