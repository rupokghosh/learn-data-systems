Read committed and snapshot isolation

Two transactions that touch different data can run side by side without any trouble. Problems start when one reads data that another is changing, or when both change the same data. Serializable isolation would make all of this disappear, but most databases run at a weaker level by default because it is cheaper. Weaker levels are not vague: each one rules out a specific list of anomalies and allows the rest. This lesson covers the two levels you are most likely to be running on right now.

Read committed

Read committed makes two promises. First, no dirty reads: a transaction only ever sees data that other transactions have committed. Second, no dirty writes: a transaction never overwrites data that another transaction has written but not yet committed.

Dirty reads matter for two reasons. A reader could see some of a transaction's writes but not others, such as a seat marked sold with no matching invoice. Worse, it could see a write that is later rolled back, so it acts on data that, as far as the database is concerned, never existed. Dirty writes matter because transactions that update several rows can interleave their writes, leaving each row with a different winner.

Databases prevent dirty writes with row-level locks: before modifying a row, a transaction takes an exclusive lock on it and holds the lock until it commits or aborts. A second writer waits. Reads do not take that lock, because one long-running write would then stall every reader of that row. Instead, the database keeps the last committed value next to the uncommitted one and gives readers the committed value until the writer commits. Read committed is the default in PostgreSQL, Oracle, and SQL Server.

Read skew

Read committed still lets the data change between two reads in the same transaction. In the read skew scenario above, the report reads the sold counter before the sale commits and the free counter after it, so its numbers describe a venue that never existed. Run the report again and the totals add up. This is called a nonrepeatable read, or read skew.

For a web request that reads two rows, a brief inconsistency is often tolerable. For some workloads it is not. A backup copies the whole database over minutes or hours while writes keep arriving; if each part reflects a different moment, restoring it makes the inconsistency permanent. Analytic queries and integrity checks that scan large parts of the database have the same problem: they need all their reads to describe one point in time.

Snapshot isolation and MVCC

Snapshot isolation gives each transaction a consistent snapshot of the database as of the moment it started. Whatever commits later is invisible to it, so a long report sees one frozen state for its whole run. Writers still take row locks to prevent dirty writes, but readers take no locks, so readers never block writers and writers never block readers.

The implementation is multi-version concurrency control (MVCC). Every transaction gets an increasing transaction ID when it starts. Rows are never overwritten in place: each row version records the ID of the transaction that created it (created_by) and, once replaced or deleted, the ID of the transaction that did so (deleted_by). An update is a delete of the old version plus the creation of a new one.PostgreSQL stores these as the hidden xmin and xmax columns of every row. When a transaction reads, it walks the versions and applies a few rules:

  • Ignore versions created by transactions that were still running when this one started, even if they have committed since.
  • Ignore versions created by transactions that aborted.
  • Ignore versions created by transactions that started later.
  • A deletion counts only if the deleting transaction is visible by the same rules.

Old versions pile up, so a background process (VACUUM in PostgreSQL, purge in InnoDB) removes versions that no running transaction can see any more. A transaction left open for hours holds that cleanup back for the entire database, which is one reason to keep transactions short.

Indexes need care too. One approach lets the index point at every version of a row and has queries skip versions they cannot see; PostgreSQL adds tricks to avoid touching the index when an update stays on the same page. Another approach, used by CouchDB and LMDB, is an append-only B-tree: a write transaction copies the pages it changes up to a new root, and each root is a consistent snapshot of the whole tree.

A note on names

The SQL standard was written before snapshot isolation was described, and it defines its levels in terms of the anomalies that locking implementations allowed at the time. Vendors then mapped their own designs onto those names. PostgreSQL implements snapshot isolation and calls it repeatable read. MySQL's InnoDB also calls its level repeatable read, but it behaves differently on writes, as the next lesson shows. Oracle uses the name serializable for what is really snapshot isolation, and IBM Db2 uses repeatable read to mean serializability. The name in the documentation tells you little; test the behavior you depend on.
