Partitioning key-value data

Replication puts copies of the same data on several machines. That helps when a machine dies or when reads pile up, but every copy still holds everything. Once the dataset, or the rate of writes into it, outgrows what one machine can store or absorb, you have to split the data itself. Each record then belongs to exactly one partition, and different partitions live on different machines.This kind of partitioning is a deliberate split for scale. It has nothing to do with a network partition, which is a fault.

The names vary more than the idea. MongoDB and Elasticsearch call a partition a shard, HBase calls it a region, Bigtable a tablet, and Cassandra and Riak talk about vnodes. The goal is always the same: spread data and queries evenly, so that ten machines can carry roughly ten times the load of one.

Partitions and replicas

In practice the two techniques are combined. Each partition is replicated, so a record lives in one partition but on several machines, and a single machine holds replicas of several partitions. With leader-based replication, a node can lead some partitions and follow others at the same time. Because the replication schemes of the previous chapter apply to each partition unchanged, the rest of this chapter can mostly ignore replicas.

The real question is which partition a record belongs to. If the rule is unfair, some partitions receive more data or more queries than others. That is skew, and its extreme form is a hot spot: one partition doing nearly all the work while its neighbours idle. Placing each record on a random node would spread data perfectly, but then a reader looking for a key would have to ask every node. The rule has to be something a reader can repeat.

Splitting by key range

One rule gives each partition a continuous range of keys, the way a phone book might be bound in volumes A to D, E to J, and so on. If you know where each range starts and ends, you know which partition to ask. The ranges need not be equally wide; they need to hold about the same amount of data. Orders keyed by customer surname would need narrow ranges around common initial letters and wide ones where names are rare. An administrator can set the boundaries, or the database can choose them, as Bigtable and HBase do.

Inside a partition, keys can be kept sorted, as in an SSTable or a B-tree, so range scans are cheap. If the key is a timestamp, "every reading between 14:00 and 14:30" is one contiguous slice of one partition, or of a few neighbouring ones.

The weakness is that traffic can follow the key order. If the key is the time an event occurred, every new event sorts after all earlier ones, so every write goes to the partition that holds the latest range while older partitions receive nothing. The usual fix is to put something else first, such as the ID of the device that produced the event. Writes from many devices then land in many ranges. The cost moves to the reader: a question about all devices in one time window becomes one range scan per device.

Splitting by hash of the key

The other common rule runs the key through a hash function and gives each partition a range of hash values. A good hash turns skewed input into evenly spread output: two keys that differ in one character get unrelated hashes. The function does not have to be cryptographically strong; Cassandra uses Murmur3 and MongoDB uses MD5. It does have to give the same answer in every process.Python's built-in hash() on strings is seeded randomly per process, so two servers using it would disagree about where a key lives.

Hashing fixes the timestamp problem, because consecutive timestamps scatter across all partitions. It also destroys what made key ranges useful. Keys that were neighbours are now in unrelated places, so a range query has no choice but to ask every partition. In MongoDB's hashed sharding mode, for example, a range query on the shard key is broadcast to all shards.

Cassandra offers a middle path through compound keys. Only the first part of the primary key, the partition key, is hashed to pick a partition. The remaining columns, called clustering columns, set the sort order inside it.

CREATE TABLE readings (
  sensor_id text,
  taken_at  timestamp,
  celsius   double,
  PRIMARY KEY ((sensor_id), taken_at)
);

Readings from one sensor live together and sorted by time, so "what did sensor s137 report between 14:00 and 14:30?" reads one slice of one partition, while thousands of sensors still spread over the cluster. What you give up is the same question across all sensors at once, which again has to ask every partition.

Hot keys and skewed workloads

Hashing spreads keys, not requests. When one key is far more popular than the rest, every request for it still lands on the partition that owns it. Picture a ticketing site in the minute a stadium tour goes on sale, with a large fraction of all writes aimed at one event ID. No partitioning rule can split a single key, because the whole point of the rule is that a key always maps to the same place. Real traffic is often shaped like the Zipf-like pattern above: no single celebrity, but a long tail with a few keys far busier than the rest.

Most databases leave this problem to the application. A common trick is to salt the hot key with a small random suffix, so that writes to event 7781 become writes to 7781#00 through 7781#31, which hash to different partitions. Salting moves the cost to reads. Fetching the event now means reading every salted key and merging the results, and the application has to track which keys are salted, since salting the many keys with ordinary traffic would only multiply their read cost. With key ranges, a suffix does nothing at all: the salted keys sort next to each other and stay inside one range, so the random part would have to go at the front of the key. Some managed services react to heat on their own; Amazon DynamoDB can split a busy partition, but even it cannot spread one item across machines. For a key you expect to be hot, the decision is still yours, and it depends on knowing your traffic.
