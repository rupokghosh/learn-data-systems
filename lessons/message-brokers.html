Transmitting event streams

A batch job reads a finished, bounded input and produces an output some minutes or hours later. Most real data never finishes arriving, though. Players keep making moves, sensors keep reporting, customers keep paying. If you want results that are seconds old rather than a day old, you stop waiting for the input to end and process each piece as it appears. That piece is an event: a small, immutable record that something happened at a particular time.

Producers, consumers, and topics

An event is written once by a producer and read by any number of consumers. Related events are grouped into a topic (also called a stream).A file or a database table could hold events too, but then consumers must poll. The more often they poll, the more each empty poll costs. Streaming systems instead notify consumers when something new arrives. The open questions are how the event gets from one to the other, and what happens when the two sides do not run at the same speed.

The simplest answer is to send events directly. UDP multicast feeds in trading systems, brokerless libraries such as ZeroMQ, and webhooks (an HTTP call to a URL the consumer registered) all work this way. They are fast, but the application has to handle loss: if a consumer is offline when the event is sent, it misses it.

A message broker is a server built to take the buffering job off both sides. Producers write to it and move on; consumers read from it at their own pace. Because the broker sits in the middle, clients can come and go, and the broker decides how durable the buffer is. There are two quite different designs.

Brokers that delete what they deliver

Traditional brokers such as RabbitMQ, ActiveMQ, and the cloud queue services follow the style of the AMQP and JMS standards. The broker pushes each message to a consumer and waits for an acknowledgement. Once acknowledged, the message is deleted. If the connection closes before the acknowledgement arrives, the broker assumes the work was not done and delivers the message again.

With several consumers on one queue, you choose between two patterns. Load balancing hands each message to one consumer, which spreads expensive work across workers. Two properties fall out of this design. First, order is not preserved under load balancing: a redelivered message is processed after messages that were sent later, which matters if a later message depends on an earlier one. You can avoid that only by giving each ordered stream its own queue with a single consumer. Second, the history is gone. Once a message is acknowledged, no new consumer can ever read it, so you cannot add a new system later and have it start from the beginning.

Brokers built on a log

A log-based broker, such as Apache Kafka, Amazon Kinesis Data Streams, or Apache Pulsar, keeps messages in an append-only log on disk and does not delete them when they are read. A producer appends to the end; a consumer reads sequentially and remembers how far it got. To scale beyond one machine, a topic is split into partitions, each an independent log on a different broker node. Every message in a partition gets a monotonically increasing offset.

Producers choose the partition by hashing a key, so all events with the same key land in the same partition and stay in order. Consumers that share work form a consumer group, and the broker assigns each partition to exactly one member of the group. Within a partition, messages are therefore processed one at a time, in order, by a single consumer.The price is coarse parallelism: a group can use at most as many consumers as the topic has partitions, and one slow message holds up everything behind it in its partition.

Instead of acknowledging each message, a consumer periodically commits its offset per partition. If it crashes, the partition moves to another member, which resumes from the last committed offset. Anything processed after that commit is processed again.

Try committing every message and crashing a consumer: nothing is repeated, but you pay for a commit on every message. Commit every ten and the duplicate count jumps after each crash. This is why consumers of a log are said to get at-least-once delivery, and why their side effects should tolerate repeats, a theme the last lesson in this chapter returns to.

Retention, lag, and replay

The log cannot grow forever, so it is split into segments and old segments are deleted after a configured time or size. That makes the log a bounded buffer on disk. Disks are large: a few terabytes at typical write rates hold days or weeks of messages, which is far more slack than an in-memory queue can offer. A consumer that falls behind does not slow the producer or other consumers. It only slows itself, and the distance between its offset and the end of the log, its lag, is the number to alert on. If lag exceeds retention, the consumer skips messages it never saw.

Because reading does not delete anything, the consumer's offset is the only state that changes, and it is under your control. Move the offsets back and the group processes yesterday's messages again, into a new output, with new code. That turns reprocessing from a risky manual operation into an experiment you can run, compare, and throw away, much like rerunning a batch job.

The rule of thumb follows directly. If messages are expensive, independent jobs where order does not matter, such as rendering invoices or resizing images, a traditional queue spreads the work best. If messages are a high-volume stream where order matters and you may want to add consumers or reprocess later, a partitioned log fits better.
