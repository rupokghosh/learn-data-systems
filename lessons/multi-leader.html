Multi-leader replication

Single-leader replication has one obvious weakness: every write goes through one machine. If a client cannot reach the leader, because of a network problem or because the leader is in another part of the world, it cannot write at all. The natural extension is to let more than one node accept writes. Each leader takes writes locally and forwards them to the others, so every leader is also a follower of every other leader.

This buys availability and latency, and pays for them with the hardest problem in replication: two leaders can accept conflicting writes at the same time, and someone has to decide what the data looks like afterwards.

When more than one leader makes sense

Inside a single data centre, multi-leader replication rarely earns its complexity. It shows up in three situations.

  • Several data centres. Put a leader in each region. Writes are handled locally and replicated between regions asynchronously, so users do not pay a cross-ocean round trip on every write, a region can keep working when another one is down, and a flaky link between regions does not stall writes. Tools in this space include BDR for PostgreSQL and Tungsten Replicator for MySQL; several cloud databases offer it as a managed option.
  • Clients that work offline. A notes or calendar app that must work on a plane keeps a local database on each device. Every device is a leader, and syncing is multi-leader replication with a replication lag of hours. CouchDB and its in-browser sibling PouchDB were designed for this.
  • Collaborative editing. When several people edit one document at once, each person's local copy accepts their keystrokes immediately and changes flow between them. The unit of change is tiny, a keystroke, but the conflict problem is the same.

Multi-leader support is often bolted onto a database that was designed for one leader, and features such as auto-increment keys, triggers, and integrity constraints can behave surprisingly once two nodes write at once.Auto-increment is the classic trap: two leaders both hand out the next ID. A common workaround gives each leader its own interleaved sequence, for example odd and even numbers.

Write conflicts

A team of three is planning an offsite, and the destination lives in one record. Amara in Frankfurt, Kenji in Singapore, and Luis in São Paulo each change it within the same second. Each change succeeds immediately at the local leader. Only later, when the changes are replicated, does each data centre discover that another leader changed the same record from the same starting value. With a single leader the second writer would have waited, or been told the record had changed. Here every writer was told "saved".

Conflict detection could be made synchronous, by waiting for every leader to agree before confirming, but then you have rebuilt single-leader replication with extra steps and lost the reason for having several leaders. So conflicts are detected after the fact, and the system must then converge: every replica has to end up with the same value, whatever order the changes arrived in.

Resolving conflicts

The simplest strategy is to make conflicts impossible. Conflict avoidance routes every write for a given record to the same leader, for example the home data centre of the user or team that owns it. For that record, the system behaves like single-leader replication. It is the most widely recommended approach, and it breaks down when the home data centre fails or the owner moves, because then writes have to be rerouted and conflicts become possible again.

When conflicts can happen, the replicas have to converge on one outcome. The options, all of which you can try above:

  • Last write wins. Attach a timestamp or unique ID to every write and keep the highest. Simple and popular, and it throws data away without telling anyone. Clocks on different machines disagree, so "last" is not even reliably last.
  • Priority by replica. Let writes from a designated replica win. Just as lossy, with a different victim.
  • Merge. Combine the values, for example by sorting and joining them. Nothing is lost, and for sets, counters, and lists this is often exactly right. For a single choice such as a destination, the merged value means nothing.
  • Record the conflict and let application code decide. Keep every version. A conflict handler can run as soon as the conflict is detected, without a human, or the versions can be shown to the next reader, often a person, who picks one. CouchDB works the second way.

Writing correct custom resolution is surprisingly hard, which is why there is active work on data types that resolve conflicts automatically and sensibly: conflict-free replicated data types (CRDTs), used in Riak and in collaborative editors, and operational transformation, the algorithm behind many real-time document editors.

Replication topologies

With more than two leaders, you also choose the paths writes travel. In a circular topology each node forwards to the next, which was long MySQL's default. In a star, one hub forwards to everyone. In all-to-all, every leader sends directly to every other. To stop a write from looping forever, each write carries the IDs of the nodes it has passed through, and a node ignores writes it has already seen.

Circular and star topologies have a weak spot: a write has to pass through intermediate nodes, so one failed node can cut others off until someone reconfigures the topology. All-to-all avoids that, but brings its own problem. Some links are faster than others, so writes can overtake each other. If one leader inserts a row and another updates that row, a third leader can receive the update first.

Attaching timestamps does not fix overtaking, because clocks cannot be trusted to order events across machines. The fix is to track which writes each write depends on, with version vectors, which the lesson on concurrent writes builds up step by step. Many multi-leader systems implement conflict detection and causal ordering poorly, so if you run one, test these scenarios before you rely on it.
