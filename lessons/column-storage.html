Analytics and column storage

Every engine so far was built for the same kind of request: find a few records by key, then insert or update a few more. A user opens their playlist, a checkout reserves an item, a sensor reports a reading. That pattern is called online transaction processing, or OLTP, and it is what most application databases spend their lives doing.

Businesses also ask a second kind of question. How many minutes of jazz were streamed in Brazil last week? Which tracks lose listeners in the first thirty seconds? Answering means scanning millions of records, touching only a few columns of each, and boiling them down to a handful of numbers. That pattern is online analytic processing, OLAP, and it wants a very different storage layout.

Running heavy analytic queries on the production database is risky: one big scan can starve the requests your users are waiting on. So most companies copy their data into a separate data warehouse. Data is extracted from the operational systems, transformed into an analysis-friendly shape, and loaded into the warehouse, a process called ETLETL: Extract, transform, load. It may run as a nightly batch or as a continuous stream of changes from each source database.. The warehouse can then use storage built purely for reading: Vertica, Amazon Redshift, Snowflake, BigQuery, and ClickHouse are examples, as are open-source query engines such as Trino and Spark SQL that read files directly.

Warehouse tables are usually arranged as a star schema. At the center sits a fact table where each row is one event: here, one play of one track. Its columns are either measurements, such as seconds played, or references to dimension tables that describe the who, what, where, and when of the event.

Storing columns instead of rows

Fact tables are where the size is: billions of rows, often a hundred or more columns wide. Yet a typical analytic query reads only three or four of those columns. A conventional row-oriented engine, whether B-tree or LSM, stores all of a row's values next to each other. To sum one column it must pull every row off the disk, all hundred columns of it, and throw most of the bytes away.

Column-oriented storage flips the layout. All the values of one column are stored together, typically in a file of their own, and a query reads only the files for the columns it names. The one rule is that every column file keeps rows in the same order, so the 9th value of track_id and the 9th value of seconds belong to the same play. Parquet, the most widely used columnar file format, follows the same idea inside each file.

The last query is the exception that explains why OLTP databases stay row-oriented. Reading one complete record from a column store means visiting every column file and reassembling the row. Columnar layouts trade fast single-record access for fast scans, and analytics is almost all scans.

Compression: bitmaps and runs

Storing a column on its own has a second payoff: the values in a column look alike. A fact table may have billions of rows but only a few thousand distinct tracks, a few dozen countries, a handful of device types. Repetitive data compresses well, and one technique fits columns especially well: bitmap encoding. For each distinct value, keep a bitmap with one bit per row, set to 1 where the row has that value.

When there are few distinct values, the bitmaps are small enough to store as they are. When there are many, each bitmap is mostly zeros, and run-length encoding squeezes it further by storing the lengths of alternating runs of 0s and 1s instead of the bits.

Bitmaps also make filtering fast. WHERE track_id IN (31, 47) becomes a bitwise OR of two bitmaps, and a condition on a second column becomes a bitwise AND with that column's bitmap. Because the k-th bit of every bitmap refers to the same row, the CPU can combine them a whole machine word at a time. Analytic engines go further and process compressed column chunks in tight loops that fit in the CPU cache and use SIMD instructions, an approach usually called vectorized execution.

Sort order, writes, and precomputed answers

Column files have to share a row order, but that order does not have to be arrival order. A column store can sort its rows by a key the administrator picks, for example by date and then by track. Queries that filter on date can then skip whole ranges, and as the toggle above shows, the first sort column compresses dramatically, because equal values sit in long runs. The second sort column compresses well within each run of the first, and later columns look close to random. Vertica, which grew out of the C-Store research project, can keep several copies of the same data sorted different ways, so each query can use the copy whose order suits it best.

Sorted, compressed columns are terrible at in-place updates: inserting one row in the middle would mean rewriting every column file. The answer is one you have already met. Writes go first to an in-memory store, and are merged into the column files on disk in large batches, much like an LSM-tree's memtable and compaction. Queries read both and combine the results. ClickHouse's MergeTree engine, for instance, writes each batch as an immutable sorted part and merges parts in the background.

Finally, if the same aggregates are asked for again and again, why recompute them? A materialized view stores a query's results on disk and updates them when the underlying data changes. A data cube is a special case: a grid of totals along several dimensions at once, such as seconds played per track per day. Summing one row of the grid answers "per track", summing a column answers "per day", with no scan at all. The cost is flexibility: a question about any attribute that is not a dimension of the cube, such as listeners on the family plan, needs the raw data again. That is why warehouses keep the raw facts and treat cubes as an accelerator, not a replacement.
