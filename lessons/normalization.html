Many-to-one, many-to-many, and normalization

Many sign-up forms ask where you live with a dropdown instead of a free-text box. The dropdown is not only there to fix spelling. It decides whether the database stores the words "Bangalore" in every profile, or stores a small number that points at the one row describing that city. That decision shows up later in surprising places: how many writes an update costs, whether your data can contradict itself, and which data model handles your application gracefully.

IDs versus duplicated text

Storing an ID has real advantages. Every profile shows the same spelling. There is one list of cities to search, to translate, or to attach a time zone to. And when something about a city changes, it changes in one place. The ID itself means nothing to people, so it never has to change; everything that does mean something lives in exactly one row.Removing duplication like this is called normalization. The formal normal forms go much further, but the working rule is short: if a fact is stored in two places, sooner or later the two copies will disagree.

The cost is that profiles now refer to cities. Many profiles point at the same city, which makes this a many-to-one relationship, and showing a profile now takes a join.

With duplicated text the rename costs one write per profile, and that number grows with your user base. If the process dies partway through, nothing records which rows were missed. The database now holds both spellings, and every query that filters or groups by city quietly returns wrong answers. In a relational database a single UPDATE ... WHERE city = 'Bangalore' runs as one transaction, so it either finishes or rolls back, but it still has to find and lock every copy. A bulk update in a document store such as MongoDB's updateMany is atomic only per document, which is exactly the failure shown above.MongoDB added multi-document transactions in version 4.0, released in 2018. Before that, a half-finished bulk update was simply possible.

With an ID, the rename is one write to one row, and every profile shows the new name the next time it is read. There is no halfway state to land in.

Duplication is not always a mistake. Denormalizing, keeping a deliberate copy, is a standard way to make reads faster: a search index, a cache, or a feed that stores each author's name next to each post all trade extra write work and the risk of inconsistency for cheaper reads. The difference is intent. You choose which copy is the source of truth, and you build the machinery that keeps the others up to date.

Joins, and where they happen

Normalized data needs joins to put it back together. In a relational database that is routine, and the query planner decides how to do it:

SELECT p.name, c.name AS city
FROM profiles p
JOIN cities c ON c.id = p.city_id
WHERE p.id = 104;

Document databases designed around self-contained trees often have weak join support. Then you either duplicate the city name into every document, with the problems above, or you store the ID and do the join yourself in application code:

const profile = await db.profiles.findOne({ _id: 104 });
const city = await db.cities.findOne({ _id: profile.city_id });
return { ...profile, city: city.name };

That works, but the join has moved out of the database, where an optimizer could choose indexes and batch lookups, and into your code, where you write it, test it, and maintain it for every screen that needs it.

Data also tends to become more connected as a product grows. Version one of a profile stores the employer as a string. Version two turns employers into pages with their own logos and updates, so each position now references an organization. Version three lets people endorse each other, and each endorsement should show the endorser's current name and photo. Every step adds references between entities, and references are where tree-shaped documents start to struggle.

Many-to-many relationships

Membership in organizations is many-to-many: one person belongs to several organizations, and each organization has many members. Neither side owns the other, so no single tree can hold the relationship without copying something. The relational answer is a third table whose rows are just pairs of IDs.

"Which organizations is Priya in?" and "Who belongs to Harbor Bank?" are the same kind of query: one join through the same table, with an index on each of its two columns. A document model cannot express this symmetrically. Whichever side you nest the list inside, the other direction becomes either a scan of every document or a second copy that you must keep in sync.

This is an old argument in a new form.IBM's IMS, built in the late 1960s for the Apollo program, stored data as trees much like JSON documents. The competing network model, standardized by CODASYL, allowed records with several parents, but programmers had to navigate the links by hand. The relational model replaced both, largely because a query optimizer could choose the access path instead. Hierarchical databases of the 1960s handled one-to-many data well and many-to-many data badly, for the same reasons document databases do today.

Schema-on-read and schema-on-write

Document databases are often called schemaless, which is misleading. Any code that reads the data assumes some structure: it expects a field called city_id to exist and to hold a number. The schema is still there. What changes is when it is enforced.

With schema-on-write, the database checks every write against a declared schema, as relational databases do. With schema-on-read, the structure is implicit and only interpreted when the data is read.It is the same split as static and dynamic type checking in programming languages, and it attracts the same arguments. The difference becomes concrete the day the structure changes. Say you have stored a single full_name and now want first names separately, to greet people by name.

Schema-on-write changes the schema and then migrates the existing rows:

ALTER TABLE users ADD COLUMN first_name text;
UPDATE users SET first_name = split_part(full_name, ' ', 1);

In PostgreSQL the ALTER TABLE is nearly instant, because adding a nullable column only changes the catalog. The UPDATE is the expensive part: it rewrites every row. On a large table you would backfill in batches, or leave the column empty and fill it in as rows are touched.

Schema-on-read skips the migration. New code writes the new field, old documents keep their old shape, and every reader handles both:

function firstName(user) {
  if (user.first_name !== undefined) return user.first_name; // written by new code
  return user.full_name.split(" ")[0];                       // older documents
}

Neither approach is free.Splitting on the first space is wrong for plenty of real names. Many cultures write the family name first, and some people have a single name. The code is easy; deciding what the data means is not. Schema-on-write moves the cost up front into a migration, and keeps every reader simple. Schema-on-read spreads the cost across every piece of code that reads the data, forever. It earns its keep when records are genuinely varied, such as many kinds of events with different fields, or data shaped by an outside system that changes without warning. When all records share one structure, an explicit schema documents that structure and enforces it, and both camps now offer it: PostgreSQL has constraints and typed columns, and MongoDB can validate documents against a JSON Schema.
