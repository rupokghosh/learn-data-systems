Declarative and imperative queries

The relational model did not only change how data was stored. It changed how you ask for it. Databases before it, such as IBM's IMS and the CODASYL systems, were queried with imperative code: the program stepped from record to record, following pointers, in an order the programmer chose. SQL is declarative. You describe the result you want, the conditions it must meet and the shape it should have, and the database works out how to produce it.SQL follows the structure of Codd's relational algebra fairly closely: selection, projection, and joins over sets of rows, with no notion of a loop.

That sounds like a matter of taste. It is not. Leaving out the "how" is exactly what lets the database get faster without anyone rewriting their queries.

Saying what, not how

Here is the same question asked both ways: which products cost less than $15 and are in stock?

// Imperative: a recipe
const cheap = [];
for (let i = 0; i < products.length; i++) {
  const p = products[i];
  if (p.price < 15 && p.inStock) {
    cheap.push(p.name);
  }
}
-- Declarative: a description
SELECT name
FROM products
WHERE price < 15
  AND in_stock;

The loop commits to a lot. Start at element zero. Look at each element in turn. Append matches to the array in the order you find them. The SQL commits to almost nothing: it does not say which rows to look at first, whether to use an index, how many CPU cores to use, or what order the answers come back in. Watch what the database does with that freedom.

Both strategies return the same six products. But notice the order. The loop returns them in the order they sit in the array, because that is what the code says. The parallel query returns them in whatever order the workers happen to find them, and the index scan returns them sorted by price. All three are correct, because the SQL never asked for an order. If you need one, you say so with ORDER BY, and the planner takes that into account too.

Why leaving things out helps

A declarative query hands three decisions to the database, and each one is a chance to improve without touching application code.

The access path. The query optimizer chooses between scanning the whole table and using an index, picks the order of joins, and decides which join algorithm to use, based on statistics about the data. When the table grows from a thousand rows to a hundred million, the plan changes; the query text does not. You can add an index next year and every existing query that benefits will start using it.Run EXPLAIN in front of a query in PostgreSQL or MySQL to see the plan the optimizer chose. The plan shown in the widget imitates PostgreSQL's format.

The physical layout. Because no query depends on where rows live or what order they are stored in, the database can reorganize storage, compress pages, or reclaim space without breaking anyone. An imperative program that relied on rows arriving in insertion order would break the moment the storage engine moved them.

Parallelism. CPUs now get faster mainly by adding cores. Imperative code describes a sequence of steps, and each step might depend on the one before, so it is hard to split safely across cores or machines. A declarative query only describes a pattern the result must match, so the database is free to split the work. PostgreSQL added parallel sequential scans in version 9.6 and turned them on by default in version 10. Queries that could benefit did so without anyone rewriting them.

The trade-off is control. Sometimes the optimizer picks badly, and you end up nudging it with indexes, rewritten queries, or hints. And some computations are awkward to state declaratively at all. That is why most systems let you drop down to imperative code when you must, but treat it as the exception.

The same idea in the browser

Declarative languages are not unique to databases. Suppose a billing page should show the amount in red for every overdue invoice. In CSS that is one rule:

tr.overdue td.amount { color: crimson; }

The imperative version walks the DOM and sets styles by hand:

for (const row of document.getElementsByTagName("tr")) {
  if (!row.classList.contains("overdue")) continue;
  for (const cell of row.children) {
    if (cell.classList.contains("amount")) cell.style.color = "crimson";
  }
}

The loop runs once. When an invoice is paid and loses its overdue class, its amount stays red until you write more code to undo it. When new rows arrive, someone must remember to run the loop again. The CSS rule simply keeps describing what should be true, and the browser keeps it true. Browser engines are also free to match selectors however they like; Firefox, for example, computes styles in parallel across cores.

MapReduce: somewhere in between

MapReduce, popularized by Google and by Hadoop, sits between the two styles. You write two small functions in an ordinary programming language, and the framework decides where and in what order to run them across many machines. Here is monthly revenue from paid orders, using MongoDB's mapReduce:

db.orders.mapReduce(
  function () { emit(this.placedAt.toISOString().slice(0, 7), this.total); },
  function (month, totals) { return Array.sum(totals); },
  { query: { status: "paid" }, out: "revenue_by_month" }
);

The functions must be pure: they may not touch anything outside their inputs, and the reduce function must give the same answer however its inputs are grouped, because the framework may call it several times on partial results. That restriction is what lets the framework run the functions anywhere, in any order, and rerun them after a machine fails.The query option is a small declarative filter applied before the map step, so even this API mixes the two styles.

But writing two carefully coordinated functions is harder than writing one query, and the database cannot look inside a JavaScript function to optimize it. So MongoDB added the aggregation pipeline, a declarative query language written as JSON, and has deprecated mapReduce in its favor since version 5.0:

db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: {
      _id: { $dateToString: { format: "%Y-%m", date: "$placedAt" } },
      revenue: { $sum: "$total" } } }
]);

Put that next to the SQL version, and the family resemblance is hard to miss:

SELECT to_char(placed_at, 'YYYY-MM') AS month, sum(total) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY month;

A system that started out avoiding SQL ended up reinventing a declarative query language, because that is what lets the database do the optimizing.
