Reasoning about time

Once events are flowing through a broker, something has to consume them. A stream processor reads one or more input streams and does one of three things with what it computes: writes it to a store that others query, pushes it to a person as an alert or a dashboard update, or emits it as another stream for the next processor. Most of the interesting ones aggregate over time, and that is where things get subtle, because a stream has two clocks and they rarely agree.

What stream processors are for

Complex event processing (CEP) systems such as Esper let you register a pattern, and they emit a match when the stream contains it. A stadium might watch for the same ticket barcode accepted at two different gates within a minute, a sign of a copied ticket. The usual relationship between data and query is inverted: the queries are stored for a long time, and the events flow past them.

Stream analytics cares less about specific sequences and more about aggregates: scans per minute at each gate, the 99th percentile of checkout latency over the last five minutes, a rolling average compared with last week. Apache Flink, Kafka Streams, and Spark Structured Streaming are built for this. Some analytics use probabilistic structures, such as HyperLogLog for counting distinct visitors, which trade a small, known error for a large saving in memory.

Two other uses come up constantly. Maintaining materialized views, such as keeping a cache or search index up to date from a change stream, is stream processing even though nobody calls it analytics. And search on streams stores queries instead of documents: a saved search for "two-bedroom flat under 1,500 near the river" is matched against each new listing as it arrives. Elasticsearch's percolator feature works this way.

Event time versus processing time

Every event has an event time, when it actually happened, and a processing time, when the stream processor gets to it. Normally the gap is milliseconds. But a phone may queue events while offline, a broker may hold a backlog while a consumer is redeployed, and a processor that restarts after a crash reads minutes of buffered events in a burst.Reprocessing old data is the extreme case: events from last month are processed today. A computation that uses processing time cannot produce the same answer twice.

If you window by processing time, those delays become fiction in your output. A three-minute outage of the processor shows up as three minutes of zero traffic followed by a spike that never happened. Windowing by event time is correct, but raises a new question: since events can arrive late, when do you know a window is finished?

Windows and stragglers

There are four common shapes of window:

WindowDefinitionTypical use
TumblingFixed length, back to back, no overlap. Every event belongs to exactly one.Scans per minute.
HoppingFixed length, starting every hop, so consecutive windows overlap.A five-minute average updated every minute.
SlidingAll events within a fixed interval of each other, however they line up with the clock."More than 30 scans within any 10 seconds."
SessionNo fixed length. A window grows while events keep coming and closes after a gap of inactivity.A visitor's browsing session.

Whatever the shape, an event-time window can only be published once you believe no more events for it will arrive. You can never be sure: a scanner may have been offline for an hour. Processors track a watermark, an estimate of how far event time has progressed, commonly the largest event time seen so far minus an allowed lag. When the watermark passes the end of a window, the window is published. Events that turn up after that are stragglers, and you have two options. You can drop them, and perhaps count how many you dropped so you notice when it becomes a lot. Or you can publish a correction, an updated value for a window you already emitted, which only works if downstream systems can overwrite earlier results.

Whose clock?

Event time has to come from somewhere, usually the device where the event happened, and device clocks cannot be trusted. A phone's clock may be wrong by minutes, or set deliberately to cheat in a game. A common remedy is to log three timestamps: when the event occurred by the device clock, when the device sent it by the device clock, and when the server received it by the server clock. The difference between the last two estimates the device's clock offset, ignoring network delay, which is small next to an offset of minutes. Apply that offset to the first timestamp.

The practical guidance is short. Carry an event-time timestamp in every event from the moment it is created. Window by event time unless you genuinely want to measure the processor itself. Choose the watermark lag from measured delays rather than guesswork, track how many stragglers you drop, and decide up front whether consumers of your results can handle corrections.
