B-trees

Log-structured engines became popular relatively recently. The B-tree is far older: it was published by Rudolf Bayer and Edward McCreight in 1970, and within a decade it was the standard index structure in databases. It still is. Almost every relational database, including PostgreSQL, MySQL's InnoDB, SQL Server, Oracle, and SQLite, stores its indexes (and often the tables themselves) in B-trees, and so do many non-relational stores.

Like an SSTable, a B-tree keeps keys in sorted order, so point lookups and range scans are both efficient. Beyond that, the two designs pull in opposite directions. An LSM-tree never modifies a file once it is written. A B-tree modifies data in place, on a fixed grid of pages.

Pages and references

A B-tree divides the database file into fixed-size pagespage: The unit a B-tree reads and writes. PostgreSQL uses 8 KB pages and InnoDB 16 KB by default. Disks also work in fixed-size blocks, so a page maps neatly onto them., and always reads or writes a whole page at a time. Each page has an address, and a page can refer to another page by that address, much like a pointer, except that it points into a file on disk instead of into memory.

One page is the root. It holds a handful of keys that act as boundaries, with a page reference between each pair. The reference between keys 35 and 65, say, leads to a page responsible for every key from 35 up to (but not including) 65. That child splits its range further, and so on down to the leaf pages, which hold the keys themselves together with their values, or with a reference to where the full row lives.

The number of references in one page is the branching factor. Real pages hold hundreds of keys, so the branching factor is in the hundreds too. The tree below uses tiny pages of at most three keys, so you can watch the structure change.

Inserts and page splits

To look up a key, start at the root, pick the reference whose range covers the key, read that page, and repeat until you reach a leaf. The number of pages you read equals the depth of the tree. To update a value, do the same lookup and overwrite the value inside its leaf page, then write that page back to the same place on disk. No other page changes.

To insert a new key, find the leaf whose range covers it. If the leaf has room, add the key and write the page back. If it is full, split it: move the upper half of its keys into a brand new page, and add a new separator key to the parent so that lookups know which half to visit. If the parent overflows as a result, it splits too, and the separator moves up another level.

The only way the tree gets deeper is when the root itself splits. Then a new root is created above it, with one separator and two children. Growth happens at the top, never at the bottom, so every leaf is always the same distance from the root. That property, being balanced, is what guarantees that a tree of n keys is only about logb n pages deep, where b is the branching factor.

Notice what the toy above makes visible. Splits leave pages half empty, so a B-tree built from random inserts typically has pages around two-thirds full. That unused space is one of the costs the next lesson measures.

How deep is deep?

Logarithms with a base in the hundreds grow astonishingly slowly. Choose a page size and a key size below, and see how much data a tree of a given depth can reach.

With 8 KB pages and small keys, four levels already reach tens of gigabytes and five levels reach terabytes. Just as important, almost all of the tree's pages are leaves. The interior levels are a small fraction of the total, so the database keeps them in its buffer cache, and a lookup usually costs a single real disk read.

Crash safety and concurrency

Overwriting pages in place is the B-tree's defining move, and its main hazard. A split writes at least three pages: the old page, the new page, and the parent. If the machine dies after writing some of them, the tree can be left with a page that nothing points to, or a reference to a page that was never written.

The standard defense is a write-ahead log (WAL)InnoDB calls it the redo log. PostgreSQL calls it the WAL, and also ships it to replicas.: an append-only file that records every change before it is applied to the pages. After a crash, the database replays the log to bring every page to a consistent state. The cost is that every change is written at least twice, once to the log and once to the page.

Concurrency needs care for the same reason. If one thread is halfway through a split, another thread descending the tree must not follow a reference into a page that is not ready. B-tree implementations protect pages with latches: short-lived, lightweight locks held only while a page is being read or changed, as opposed to the transaction-level locks that protect your rows. Log-structured engines have it easier here, because they build new files in the background and swap them in atomically.

Decades of use have produced many refinements. Some engines, such as LMDB, never overwrite a page: they write the modified copy elsewhere along with new copies of its parents up to the root, which doubles as crash protection and gives readers consistent snapshots for free. Interior pages can store shortened keys, since a separator only needs enough bytes to tell two ranges apart, which raises the branching factor. And leaf pages often carry references to their left and right siblings, so a range scan can walk across the leaves without climbing back up the tree.
