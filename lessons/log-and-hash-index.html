The log and the hash index

Strip a database down to its job and two operations remain: keep the data you hand it, and give it back when you ask. Everything else a storage engine does is about making those two operations fast, cheap on disk, and safe when the power goes out.

You will rarely write a storage engine yourself, but you will pick one, tune one, and debug one at three in the morning. Knowing what it does with your bytes tells you which workloads it loves and which ones it quietly hates. This lesson builds the simplest engine that works, then fixes its problems one at a time. That path is close to the one real key-value stores took.

A database in two functions

Here is a complete, if naive, key-value store. Writing appends one line to a file. Reading walks the whole file and remembers the last line whose key matches, because a later write to the same key replaces an earlier one.

// db.js: a key-value store in two functions
const fs = require("fs");

function set(key, value) {
  fs.appendFileSync("data.log", `${key},${value}\n`);
}

function get(key) {
  let latest;
  for (const line of fs.readFileSync("data.log", "utf8").split("\n")) {
    const comma = line.indexOf(",");
    if (line.slice(0, comma) === key) latest = line.slice(comma + 1);
  }
  return latest;
}

The file is a loglog: Here, an append-only sequence of records on disk, not the human-readable text an application prints for debugging.: records are only ever added at the end, never changed in place. That makes set about as fast as a disk write can be. There is no seek to find the right spot, no read before the write, and no risk of half-overwriting an old value if the machine dies mid-write. Many real databases keep an append-only log at their core for exactly these reasons.

The price is paid by get. It reads every record ever written, so a database with ten times more history answers every query ten times slower. To read efficiently we need an index: extra data, derived from the log, that points straight at the record we want.

Adding a hash index

The simplest index is a hash map kept in memory that maps each key to the byte offset of its latest record. A write appends to the log and then updates the map. A read looks up the offset, seeks there, and reads one record. This is essentially how Bitcask, the original storage engine behind the Riak database, works: its in-memory map is called the keydir, and each entry names a file and a position in it.

Every index is a trade. Reads get faster, but every write now does extra work to keep the index current. That is why databases do not index everything by default and leave the choice to you, since you know which queries matter.

A hash index shines when there are relatively few distinct keys, each written often. Think of the latest reading for each sensor, the last time each device on a network checked in, or a shopping cart keyed by session id: lots of writes, and every key fits comfortably in memory.

Segments, compaction, and merging

An append-only file grows forever, even if you only ever update the same eight keys. The fix is to cut the log into segments. When the active segment reaches a size limit, it is closed and never written again, and a fresh segment takes new appends. Closed segments are immutable, which makes them easy to reason about: any number of threads can read them without locks.

A background process then compacts closed segments, throwing away every record that a later write has replaced and keeping only the newest value of each key. Compacted segments are small, so the same pass can merge several of them into one. The merge writes brand new files. While it runs, reads are still served from the old segments; when it finishes, the index switches to the new files and the old ones are deleted.

Deleting a key cannot erase anything, because nothing is ever modified. Instead, a delete appends a special record, a tombstonetombstone: A marker record that says "this key is deleted". It shadows every older value until compaction discards them together., and compaction drops both the tombstone and the older values it hides.

Crashes are the other half of the story. The hash map lives in memory, so a restart loses it. The engine can rebuild it by reading every segment from start to finish, which is slow for large data sets. Bitcask speeds this up by writing a compact hint file next to each segment that lists keys and offsets without the values. A crash can also leave a half-written record at the end of the log, so real formats store a checksum with each record and ignore any record whose checksum does not match.

Why append at all, instead of overwriting values in place? Sequential writes are much faster than scattered ones on spinning disks and still friendlier to SSDs. Immutable segments make crash recovery simple, since a segment is either fully written or its tail is detectably broken. And regular merging keeps the files from fragmenting over time.

Where the hash index runs out

Two limits remain. First, every key must fit in memory. A hash map on disk is possible, but each lookup and update turns into random I/O, the map is painful to grow, and collisions need careful handling. Once you have more keys than RAM, this design stops working.

Second, range queries are hopeless. A hash scatters keys on purpose, so there is no cheap way to ask for every station between ber and osl. You would have to look up every possible key one by one. The next lesson keeps the log and the segments, but stores each segment in sorted order, and both limits loosen at once.
