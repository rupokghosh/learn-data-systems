Knowledge, truth, and lies

A node in a distributed system has no shared memory to inspect and no reliable clock to consult. Everything it knows about the others arrives as messages that may be late, lost, or out of date. So the useful question is not "what is true?" but "what can a node safely conclude from the messages it has?" The answer turns out to be: less than it thinks, and very little about itself.

The majority decides

Picture a node whose outgoing network link has failed while its incoming link still works. It hears every heartbeat from its peers and believes the cluster is healthy. Its peers hear nothing from it and, after a timeout, declare it dead. Or picture a node that froze for fifteen seconds in a garbage collection pause: from its point of view no time passed at all, yet the rest of the cluster has already moved on without it. In both cases the node's own view of the situation is wrong, and it has no way to discover that by looking inward.

So distributed systems do not let any single node decide what is true. Decisions are made by a quorum, usually a majority of the nodes. If a majority declares a node dead, it is dead for all practical purposes, even if it is running perfectly well, and it must accept that verdict and step down. Majorities are used because any two of them share at least one node, so the cluster cannot reach two conflicting decisions at the same time.With five nodes, any two groups of three overlap in at least one member. This is the arithmetic behind ZooKeeper, etcd, and the consensus algorithms in the next chapter.

Leases, locks, and fencing tokens

Many systems need exactly one of something: one leader for each partition, one holder of the lock on a file, one account per username. A node may be granted that role by the majority and then lose it without knowing. If it keeps acting on its old belief, the system now has two leaders. The previous lesson showed how this happens with a lease and a long pause. Here the same failure hits a lock that protects a file in a storage service.

The fix is to stop trusting the client's belief and make the resource itself check. Every time the lock service grants the lock, it also hands out a fencing token: a number that is larger than every token it handed out before. The client must include its token with every write, and the storage service remembers the largest token it has accepted and refuses anything older. A client that slept through the loss of its lock now gets an error instead of silently destroying a newer write.

ZooKeeper provides suitable numbers for free: the transaction ID or the node version it assigns can serve as the token, since both only increase. The catch is that the storage service has to cooperate. If it cannot check tokens itself, you can sometimes get the same effect with a conditional write, such as a compare-and-set on a version number, or by putting the token into the object's name. Fencing protects against honest mistakes, such as a node that does not know it is out of date. It does nothing against a node that sends a fake token on purpose.

Byzantine faults

So far every node has been assumed to be honest: perhaps slow, perhaps confused, but never lying. A Byzantine fault is a node that sends arbitrary or deliberately misleading messages, such as claiming to have stored data it threw away or sending different answers to different peers. A system that keeps working correctly when some nodes behave like this is called Byzantine fault-tolerant, and most such protocols need more than two thirds of the nodes to be honest.

This matters in two kinds of setting. In aircraft and spacecraft, radiation can flip bits in memory and make a computer behave unpredictably, and the consequences of trusting it are severe. And when nodes belong to organizations that do not trust one another, as in cryptocurrencies and other blockchains, any participant might cheat. Inside one company's datacentre the situation is different. You run all the nodes, and a bug in your code would be present on every replica at once, so a Byzantine protocol would not save you from it. The cost of such protocols is rarely worth paying there.

Weak forms of lying are still worth guarding against. Network hardware and firmware bugs occasionally corrupt packets in ways that TCP and Ethernet checksums miss, so application-level checksums are cheap insurance. A public-facing service should validate every input: sizes, ranges, and formats, so that a malformed request cannot crash it. NTP clients query several servers and discard the ones that disagree wildly with the rest, so that one broken server cannot drag the clock away.

System models and correctness

To reason about algorithms that run on this kind of hardware, researchers write down a system model: the faults the algorithm must tolerate. There are two dimensions.

TimingWhat it assumes
SynchronousNetwork delay, pauses, and clock error all have known upper bounds. Not realistic for ordinary systems.
Partially synchronousThe system behaves within bounds most of the time but can exceed them for unknown periods. The most realistic choice.
AsynchronousNo timing assumptions at all, not even a clock. Very restrictive, but some algorithms work within it.
Node faultsWhat it assumes
Crash-stopA node that fails stops forever.
Crash-recoveryA node may crash and come back later. Data on stable storage survives, memory does not. The most useful model in practice.
ByzantineA node may do anything, including lie.

Within a model, an algorithm is correct if it satisfies stated properties. For the fencing token scheme they might be: no two grants get the same token (uniqueness), later grants get larger tokens (monotonic sequence), and a node that asks for a token and does not crash eventually gets one (availability). These properties come in two kinds. A safety property says nothing bad happens; if it is violated, you can point to the moment, and nothing afterwards can undo it. A liveness property says something good eventually happens; at any given moment it may not have happened yet, but it still could.

The difference shapes how algorithms are designed. Practical systems require safety in every situation the model allows, even if every node crashes or the network is down for an hour, because a safety violation is permanent. Liveness is allowed to come with conditions: a request is answered eventually, provided a majority of nodes is up and the network recovers. In the run where the crashed node is never suspected, no prefix of the trace proves anything is wrong, and that is exactly why timeouts exist.

A model is a simplification, and reality breaks it at the edges. Crash-recovery assumes data on disk survives, but disks fail and firmware has bugs, and a node that comes back with an empty disk can break a quorum algorithm that was proven correct. Proofs still matter, because they show an algorithm is sound within its assumptions, and testing shows how often the assumptions hold. You need both.
