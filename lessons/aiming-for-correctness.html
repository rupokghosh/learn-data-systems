Aiming for correctness

A stateless service that misbehaves can be restarted and the problem is gone. A stateful system that misbehaves keeps the damage: a wrong balance, a duplicate order, a seat sold twice. For decades the standard answer has been transactions, and they remain a fine tool. But the guarantees a database offers end at its own boundary, and many correctness failures happen just outside it.

The end-to-end argument

Lena is paying €40 for a place in a pottery class. Her browser sends the request, the app server runs a serializable transaction that inserts a payment row, the transaction commits, and the reply is lost on the way back. Lena sees an error and clicks Pay again. The second request is a new HTTP request, handled by a new transaction, which commits a second row. Every component did exactly what it promised: TCP delivered bytes without duplication, the database committed atomically, a stream processor downstream may even guarantee exactly-once processing. None of that helps, because none of those layers can tell that two different requests represent one intention.

The fix has to span the whole path, which is the end-to-end argument applied to data: a guarantee can only be fully implemented with the knowledge held at the endpoints. Generate a unique operation ID when the checkout form is rendered, send it with every attempt, and let the database reject a second use of it:

CREATE TABLE payments (
  op_id    text PRIMARY KEY,      -- minted with the form, reused by every retry
  learner  text NOT NULL,
  amount   numeric(8,2) NOT NULL
);

INSERT INTO payments (op_id, learner, amount)
VALUES ('op-5c1e', 'lena', 40.00)
ON CONFLICT (op_id) DO NOTHING;  -- a retry becomes a no-op

Any lower-level deduplication is still useful for performance, but the ID is what makes the operation idempotent from the user's point of view. Stripe's API exposes the same idea as an idempotency key header, and the pattern applies to any request that a person or a client library might repeat.

Enforcing constraints through a log

Uniqueness is the classic constraint that seems to demand coordination. Two people trying to claim the handle @tide at the same moment must not both succeed. A log offers a way to get this without distributed locks: send every claim for a given handle to the same log partition, chosen by hashing the handle, and let a single-threaded processor consume that partition in order. The first claim it sees wins; later ones are rejected. Because the log order is the same for every reader, the decision is deterministic and can be recomputed after a crash.

The same trick scales to requests that touch several partitions, without an atomic commit across them. Say a booking reserves a seat in one partition and charges a gift card held in another. First append the whole request, with its ID, to a single log partition. A stream processor reads it and emits two derived instructions, one to the seat's partition and one to the gift card's partition, each carrying the request ID. Each partition applies its instruction and ignores a repeat of an ID it has already seen. If the processor crashes halfway, it rereads the request and emits the instructions again, and deduplication makes that harmless. Atomicity comes from the request being logged once; everything after it is a deterministic derivation.

Timeliness and integrity

"Consistency" usually bundles two different properties. Timeliness means a reader sees an up-to-date state; a stale read violates it, but the violation fixes itself once the reader waits and reads again. Integrity means the data is not corrupt and no record is missing, contradictory, or duplicated; a violation stays until someone repairs it. The double charge above is an integrity failure. A gift card balance that shows the old amount for half a second is only a timeliness failure.

In most applications integrity matters far more. ACID transactions provide both at once, which is convenient but expensive across partitions. Log-based dataflow separates them: with deterministic derivation, end-to-end request IDs, and immutable events, integrity holds even though derived views lag. You can then add timeliness back where users need it, for example by having the client wait for its own request to be processed before showing the result.

Loose constraints and apologies

Many business constraints are softer than they look. A pottery class with twelve wheels may occasionally get a thirteenth booking; the studio apologizes, offers a later slot or a refund, and moves on. Businesses already handle oversold flights, out-of-stock items, and bounced payments with compensating actions, because physical reality violates constraints that software cannot see. If the cost of an apology is low, you can check the constraint asynchronously, after accepting the write, and compensate in the rare cases it fails.

Combining the pieces gives coordination-avoiding data systems: integrity preserved through logs and idempotence, constraints enforced asynchronously where an apology is acceptable, and synchronous coordination kept for the few places where a violation would be too costly to repair. Such systems can span regions and keep working through network partitions, with much less of the latency and fragility of distributed transactions.

Trust, but verify

Every guarantee rests on assumptions: that disks return what was written, that the database has no bugs, that operators do not run the wrong migration. Each of those fails sometimes. Mature storage systems such as HDFS and Amazon S3 continuously read back stored data and compare replicas to catch silent corruption. Applications deserve the same habit. Periodically recompute a derived view from the log and compare it with the live one. Check that the sum of all ledger entries matches the balances table. Restore a backup to a scratch environment and query it.

Event-based designs make this easier, because an immutable log plus deterministic derivation lets you replay and diff. Designing for auditability means being able to answer "why does this row have this value?" by pointing at the events that produced it. Cryptographic structures go further: Merkle trees and append-only signed logs, as used in certificate transparency, let outsiders check that history was not rewritten.
