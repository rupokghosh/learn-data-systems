Forward and backward compatibility

A schema change is never deployed everywhere at once. Server-side code rolls out a few machines at a time, so for minutes or hours some nodes run the new version and some run the old one. Mobile and desktop apps update whenever their users get around to it, which may be never. And the database still holds rows written by every version of the code that has ever run. For a while, often forever, old and new versions of the schema have to coexist.

Two directions

That coexistence needs compatibility in both directions:

  • Backward compatibility: new code can read data written by old code. This is the easy one, because when you write the new code you know exactly what the old data looks like and can handle it.
  • Forward compatibility: old code can read data written by new code. This is harder, because the old code was written before anyone knew what the change would be. It only works if the old code was built to tolerate things it does not understand, mostly by ignoring them.

The encodings from the previous lesson were designed with exactly this in mind, and each has a short list of rules. Break a rule and some combination of old and new code fails, or worse, silently reads the wrong value.

The rules, by format

With field tags (Protocol Buffers and Thrift), the tag is the identity of a field. You may add a field with a new tag, and old code will skip it, because the type in its header tells the parser how many bytes to jump over. The new field must be optional or have a default, because new code reading old data will not find it. You may remove a field only if it was optional, and you must never hand its tag to a different field later.Protocol Buffers has a keyword for this: reserved 3; makes the compiler reject any future field that tries to reuse tag 3. Renaming is free, since names never appear in the bytes.

With Avro, the field name is the identity, and the default value does the work that optional tags do elsewhere. You may add or remove a field only if it has a default; then whichever side lacks it uses the default. A field that may be absent is usually declared as a union with null and a default of null. Renaming is possible through aliases on the reader's schema, but only in one direction: a new reader can know the old name, while an old reader can never know the new one.

Changing a type is risky everywhere. Widening an int to a long is the classic case, and the three formats disagree on what happens when old code meets a value that no longer fits. Try it below.

A few patterns are worth noticing. Adding a required field always breaks backward compatibility, in every format, because old records do not contain it. In Avro, giving it a default fixes that; in Protocol Buffers and Thrift it does not, since a required check is not satisfied by a default, which is one reason proto3 removed required. Renames are harmless with tags and fatal in Avro without an alias. And the int-to-long change is the most instructive: Protocol Buffers truncates the number without complaint, Thrift drops the field without complaint, and Avro refuses to decode. Only one of those failures is loud, and it is the one you would prefer.

Old code that rewrites new data

Ignoring unknown fields is what makes forward compatibility work, and it creates a quieter problem. Suppose old code reads a record, changes one field, and writes the whole record back. If its decoder discarded the fields it did not recognise, the write-back erases them. Nobody sees an error, and the newer code finds its data gone the next time it looks.

The fix is for decoders to keep what they do not understand. Protocol Buffers generated classes hold unknown fields and write them back out, behaviour that proto3 lost for a while and regained in version 3.5 because of exactly this problem. The same trap exists one layer up: an ORM that maps a row onto a class, or a service that decodes JSON into a fixed struct and re-encodes it, drops anything the class does not declare. Two practical defences are to keep a catch-all for unknown fields in such models, and to prefer targeted updates, such as an UPDATE that sets one column, over read-modify-write of whole records while versions are mixed.

Rollout order matters too. If new readers must be in place before anyone writes the new field, deploy the reading side everywhere first, and only then turn on the code path that writes it, often behind a feature flag.
