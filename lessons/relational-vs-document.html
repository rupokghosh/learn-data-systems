Relational and document models

Software is built in layers, and each layer describes data in the terms of the layer below it. Your application thinks in objects and structs. Those objects are stored as tables, documents, or graphs. The database turns those into bytes in memory and on disk, and the disk turns bytes into physical state. Every layer hides the one underneath, and every layer makes some operations easy and others clumsy.

This chapter is about the second layer: the shape your data takes inside the database. It is one of the hardest decisions to undo, because queries, indexes, and application code all grow around it. Two shapes dominate general-purpose storage today: relational tables, as in PostgreSQL and MySQL, and JSON-like documents, as in MongoDB and Couchbase.

The object-relational mismatch

The relational model stores data as relations, which SQL calls tables: unordered collections of rows, where every row has the same columns.Edgar Codd proposed the relational model in 1970. By the mid-1980s relational databases had become the default way to store business data, and they still are. In the classic model each cell holds a single value, and a row cannot contain a list of other rows.

Application code rarely looks like that. In most languages one object happily holds a list of other objects: a user has a list of jobs, each job has a title and an employer. Saving that object to tables means taking it apart into rows in several tables, and loading it means putting it back together. The friction between the two shapes is called the object-relational mismatch.Also called the impedance mismatch, a term borrowed from electronics, where badly matched circuits lose signal at the connection. Object-relational mappers such as Hibernate, ActiveRecord, and SQLAlchemy write most of that translation code for you, but they cannot make the two shapes the same.

Take a professional profile. Mira has one name and one location, but several jobs and several degrees. Each of those is a one-to-many relationship: one user, many positions. In a document database the whole profile is one JSON value with the positions nested inside it. In a relational database the usual design splits it across three tables, and every position row carries a user_id pointing back to its owner.

Most values have exactly one home in each model. The user ID does not. In the document it appears once, at the top. In the tables it is copied into every child row, because that foreign key is the only thing that ties a position to its owner. The tables also need their own id for each position and degree. The document never needed those: a position is identified by where it sits inside the profile.

Locality: one read or several

When you load the profile, the document store looks up one key and reads one contiguous value. MongoDB stores each document as a single BSON blob, so the profile arrives in one piece. The relational design asks three tables. Each child table needs an index lookup on user_id to find its rows, and those rows may live on different pages on disk, far from the user row.

This advantage is called locality. If your application almost always needs the whole entity at once, for example to render a profile page, keeping it together means fewer lookups, fewer disk reads, and fewer round trips between application and database.You can fetch all three tables in one query with joins, but joining two independent one-to-many lists multiplies them: three positions and two degrees come back as 3 × 2 = 6 rows, each repeating the user's columns. Many ORMs issue one query per table for this reason.

Locality has a price. The database usually reads the whole document even when you want one field, and on many storage engines changing one field rewrites the whole document. So document designs work best when documents stay reasonably small and do not grow without bound. Appending every login event to an array inside the user's profile is a classic mistake: every write gets slower as the array grows, and MongoDB will refuse a document over 16 MB.

Locality is not exclusive to documents, either. Google Spanner lets you declare a child table as interleaved in its parent, so a user's positions are stored physically next to the user row. Oracle offers table clusters for a similar purpose. And PostgreSQL will store a jsonb column right inside an ordinary row.

When each model fits

The document model fits data that forms a tree of one-to-many relationships and is usually read as a whole: a profile, an order with its line items, a page in a content system with its blocks. Documents in one collection do not have to share the same fields, which helps when records are naturally varied, or when their structure is decided by an outside system you do not control.

It gets awkward when something outside the document needs to point inside it. You cannot refer directly to Mira's second position; you can only say "element 1 of the positions array of user 4127", and array positions shift when a new job is added at the front. It also gets awkward when documents need to point at each other. If every position should link to a shared employer record, you are back to joins, and in many document databases joins are weak or missing. MongoDB has $lookup, but in practice the work often moves into application code, which runs several queries and stitches the results together.

The relational model fits data that is highly connected, that many different queries slice in many different ways, and where you want the database itself to enforce structure and relationships.

In practice the two camps have been borrowing from each other for years. PostgreSQL (since 9.4, with jsonb) and MySQL (since 5.7) can store, index, and query JSON documents. MongoDB added $lookup joins and, later, multi-document transactions. A common, sensible design today is a hybrid: relational tables for the entities that are shared and linked, and a JSON column for the nested parts that only ever belong to one row.
