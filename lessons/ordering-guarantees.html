Ordering guarantees

Order keeps coming back in this book. A single leader exists to put all writes in one sequence. Serializability promises that transactions behave as if they ran in some order. The clocks of Chapter 8 were an attempt to tell which of two events came first. This lesson pulls those threads together, and they lead somewhere surprising: ordering, linearizability, and consensus turn out to be three faces of one problem.

Causality is a partial order

Some events must come before others because one could have influenced the other. A comment on a pull request only makes sense after the pull request exists. A refund refers to a payment. If a replica applies the refund before it has the payment, it shows a state that never existed anywhere. A system that keeps every cause ahead of its effects is causally consistent. Snapshot isolation is an example: a consistent snapshot is one that, whenever it contains an effect, also contains its causes.

Causality does not order everything. Two events on different machines, where neither node could have known about the other's event, are concurrent, and neither comes first. So the causal order is a partial order: some pairs are ordered and some are not. Linearizability is stronger. Because the system behaves like one copy with atomic operations, every pair of operations is ordered, a total order. A linearizable system therefore preserves causality automatically, which is one reason it is easy to reason about, and one reason it is expensive.

You do not have to pay for linearizability to get causality. Causal consistency is, as far as anyone knows, the strongest consistency model that does not slow down with network delay and that keeps working during a network partition. Its cost is bookkeeping: to know whether one write depends on another, the database must track what each client had seen when it wrote, typically with something like the version vectors of Chapter 5, and doing that for every operation can get heavy.

Lamport timestamps

A cheaper tool gives a total order that agrees with causality without tracking every dependency. With one leader, this is easy: the leader numbers each write in its log. Without one, the obvious schemes fail. Separate counters per node (one hands out odd numbers, another even), wall-clock timestamps, or blocks of numbers handed to each node in advance all produce numbers that can contradict causality, because one node's numbers can run ahead of another's.

Lamport timestamps fix this with two rules.Leslie Lamport described them in 1978, in "Time, Clocks, and the Ordering of Events in a Distributed System", still one of the most cited papers in the field. Every node keeps a counter. Each event on a node increments it, and the event's timestamp is the pair (counter, node ID). Every message carries the sender's counter, and a node that receives a message sets its counter to the larger of its own and the message's, then increments it for the receive event. To compare two timestamps, compare counters and break ties by node ID.

The maximum rule is what makes the order respect causality. If event x could have influenced event y, a chain of local steps and messages connects them, every hop pushes the counter strictly upward, and so x ends up with the smaller timestamp.

Point at the events in the example. Blue is everything that could have influenced the one you chose, green is everything it could have influenced, and the dashed ones are concurrent with it. Some concurrent events carry smaller numbers. That is the limit of Lamport timestamps: if x happened before y then L(x) < L(y), but the reverse does not hold, so a smaller timestamp does not prove that one event came first. Version vectors can detect concurrency; Lamport timestamps are more compact and give you a total order instead.

That total order still falls short for decisions made in real time. Suppose a theatre's ticket system runs on three nodes and must never sell seat 12A twice. Two requests for 12A arrive at almost the same moment on two different nodes. After the fact, Lamport timestamps settle it: the lower timestamp wins. The problem is the moment of decision. When node A gets its request, it must answer the buyer now. To know that its claim has the lowest timestamp, it would have to ask every other node whether it is handling a lower one, and if a node is unreachable, A cannot answer at all. The total order only exists once you have collected every operation. You also need to know when the order is final.

Total order broadcast

That missing piece has a name: total order broadcast, also called atomic broadcast. It is a protocol for sending messages to a group of nodes with two guarantees. Reliable delivery: if a message is delivered to one node, it is delivered to all of them, even if some are briefly down. Totally ordered delivery: every node delivers the messages in the same order. Crucially, the order is fixed at delivery time. A node never receives a message that slots in before one it has already delivered, which is exactly what timestamps could not promise.

This is what database replication needs. If every replica processes the same writes in the same order, every replica passes through the same states, an approach called state machine replication. ZooKeeper's Zab and etcd's Raft are total order broadcast at their core, and a single Kafka partition gives applications a similar ordered log.

Press "Both at once" a few times with the hold-back rule on: copies arrive in different orders, yet every replica gives 12A to the same person. Then switch the rule off and repeat. Each replica now applies claims in the order they happened to arrive, and sooner or later they disagree about who owns the seat.

From broadcast to linearizable storage, and back

Total order broadcast is enough to build a linearizable compare-and-set. To claim seat 12A, append a message "Ann claims 12A" to the log. Read the log, in delivery order, until your own message comes back. If the first claim on 12A in the log is yours, the seat is yours; if another came first, it is not. Every node reads the same log, so every node reaches the same verdict with no further coordination.

That makes writes linearizable. Reads from a node's local copy are not quite, because the copy may be behind the log. To fix reads, put them through the log too (append a marker and answer when it comes back), or ask for the latest log position and wait until the local copy reaches it, which is what ZooKeeper's sync does, or read from a replica that is updated synchronously.

The construction also runs the other way. Given a linearizable register with an atomic increment-and-get, stamp each message with the next number and have every node deliver in number order with no gaps: that is total order broadcast. The hard part is a gap left by a sender that crashed after taking a number, and resolving it in a fault-tolerant way is consensus. In fact all three, linearizable compare-and-set, total order broadcast, and consensus, are equivalent: a fault-tolerant solution to any one of them gives you the others.
