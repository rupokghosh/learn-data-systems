Databases and streams

A real application rarely keeps its data in one place. The same holiday-rental listing lives as a row in PostgreSQL, a document in Elasticsearch so guests can search for it, an entry in a Redis cache so the page loads quickly, and a row in the warehouse so analysts can study prices. Only one of those is the system of record. The rest are derived data, and each must hear about every change to the original. This lesson is about how that news travels, and why the answer that looks simplest is the one that breaks.

Why dual writes go wrong

The obvious approach is for application code to update every system itself: write the database, then write the search index, then invalidate the cache. This is called a dual write. It has two problems. The first is partial failure: if the database write succeeds and the index write fails, the two disagree, and making both succeed or neither would need an atomic commit across different products. The second problem is subtler and happens even when every write succeeds. In the figure, two hosts change the nightly price of the same listing at almost the same moment.

Each client did its two writes in the right order. The database saw A then B. A slow network path meant the index saw B then A. Last write wins in both places, so the winners differ. No component reports an error, and the inconsistency is permanent until the next update to that listing. You could add locks or version checks, but you would be building a distributed transaction protocol by hand across systems that were never designed to take part in one.

Change data capture

The fix is to stop having many writers. Let the application write only to the database, and let every other system follow the database's own record of what changed, in the order the database applied it. Every database already keeps such a record for replication: the MySQL binlog, the PostgreSQL write-ahead log, the MongoDB oplog. Change data capture (CDC) reads that log and publishes each change as an event, usually into a log-based broker such as Kafka. Debezium does this for several databases, and Kafka Connect moves the events into search indexes, caches, and warehouses.

This makes the database the leader and every derived system a follower. Followers can lag, because CDC is asynchronous, but they cannot disagree about order. A connector that is slow only delays the index; it cannot apply change 2 before change 1. Adding a new derived system is also easier, because it does not require touching the application code that writes.

A new follower needs a starting point, since the log usually does not reach back to the beginning of time. It takes a consistent snapshot of the database together with the exact log position the snapshot corresponds to, loads the snapshot, then applies the log from that position onward.Without the matching position you cannot tell which changes are already in the snapshot, and you either miss some or apply some twice.

Some brokers remove the need for a separate snapshot. With log compaction, the broker periodically throws away any record for which a newer record with the same key exists. A deletion is written as a tombstone, a record with a null value, which compaction eventually removes along with everything before it. What remains is one record per live key, so the compacted log is no larger than the database itself, and a consumer that reads it from offset zero ends up with a full copy. Kafka supports this per topic.

Event sourcing

Event sourcing starts from the same log, but higher up. In CDC, the application mutates rows as usual and the log is extracted from the database afterwards. Its entries are low-level: "row 88, column price, now 95". In event sourcing, the application itself records what happened as immutable events in the language of the domain, "parcel scanned at the Arnhem depot", and treats those events as the source of truth. Any table you query is derived from them.

The distinction between a request and a fact matters here. A user's request starts as a command, which may fail: you cannot deliver a parcel that is not on a van. The system validates the command against the current state, and only if it passes does it become an event. From then on the event is a fact. A later correction is a new event, not an edit.

State is a fold over the log

The table in the figure is never written directly. It is the result of starting from nothing and applying each event in turn, a left fold:

const state = events.reduce(apply, new Map());
// apply(state, event) returns the state after that one event

Seen this way, a database table and a change stream are two views of the same thing. The table is what you get by applying every change up to now; the stream is the sequence of differences between one version of the table and the next. Mutable state is convenient for reading, and an append-only log is what actually happened. Keeping the log as the source of truth brings concrete benefits:

  • Auditing and debugging. If a bad deploy corrupts derived data, you fix the code and replay. Nothing was overwritten, so nothing is lost. Accountants have kept ledgers this way for centuries.
  • Several read models from one history. The same events can build a status table for the tracking page, a per-depot workload view, and a search index, each shaped for its queries. Separating the write format from the read formats is often called command query responsibility segregation (CQRS).
  • Easier evolution. A new view can be built alongside the old one from the same events, and the old one retired when the new one is ready.

The limits are just as concrete. A dataset with heavy churn on a small number of keys produces a log far larger than its current state, and an event log, unlike a CDC change stream, cannot simply be compacted, because older events carry meaning the newest one does not. Systems therefore store periodic snapshots of the derived state to speed up recovery, while keeping the full log.Snapshots here are only an optimization: the log remains the source of truth and the snapshot can always be rebuilt from it.

Deletion is the hardest case. Privacy law such as the GDPR may require that a person's data be erased, and appending an "erased" event does not remove the address stored in earlier events. You have to rewrite history (Datomic calls this excision), or keep personal data outside the log and store only a reference to it, or encrypt it with a per-person key that you destroy on request. Even then, copies in backups and derived systems must be tracked down. Design for deletion before you commit to an immutable log, not after the first request arrives.
