Linearizability

An on-call engineer flips a feature flag to switch off a broken checkout path. The admin console confirms it, and she tells the incident channel the path is off. For the next forty seconds, some application servers keep reading the flag from a replica that has not caught up, and customers keep landing on the broken path. The system told one person that the world had changed while telling others that it had not.

Linearizability is the guarantee that rules this out. It asks a replicated system to behave as if there were only one copy of the data, and as if every operation on that copy took effect in a single instant. It also goes by atomic consistency, strong consistency, and external consistency.

One copy, atomic operations

Take a single register: one value that clients can read and write, such as a key in a key-value store or a row in a table.Linearizability is defined one object at a time. Grouping several objects into one unit is the job of transactions, a separate guarantee. Every operation takes time. A client sends a request, waits, and gets a response, and from the outside all you can observe is the interval between the two. Linearizability requires that each operation appear to take effect at one instant somewhere inside its own interval, and that the sequence of those instants be a valid history of a single register: every read returns the value of the most recent write before it.

Two rules follow. If a write finished before a read started, the read must see that write or a later one. And once any read has returned a new value, no later read may return the old one, on any client, even while the write is still in progress. A write that has not finished may or may not be visible yet; but the moment one reader sees it, everyone must.

You can test a recorded history against this definition mechanically. Look for an order of all the operations that respects real time (if one ended before another began, it comes first) and in which every read returns the latest write. If such an order exists, the history is linearizable. The checker below runs exactly that search on whatever you draw.

Try the stored histories. In the stale read, client C starts reading after the write of 1 has returned, yet gets 0; no instant inside C's bar can come before the write. The flip back is subtler. The write of 1 is still running during both reads, so either answer alone would be fine. But B has already seen 1, and C's read began after B's ended, so C cannot go back to 0. Drag C's read left until it overlaps B's and the history becomes legal: two reads that run at the same time may disagree.

Jepsen tests real databases the same way: it records histories while injecting faults and feeds them to a checker such as Knossos. The search is NP-complete in general, which is why this one stops at twelve operations.

Not the same as serializability

The two words sound alike and are easy to mix up, but they answer different questions. Serializability is an isolation property of transactions: each transaction may touch many objects, and the database promises that the result equals some serial order of the transactions. That order does not have to match real time. Linearizability is a recency guarantee for individual reads and writes of one object, and it says nothing about grouping operations.

A database can provide both, which is called strict serializability; serial execution and two-phase locking usually do. Serializable snapshot isolation, as in PostgreSQL, does not: a transaction reads from a snapshot taken when it started, so it ignores writes that committed later, even ones that finished before the read in real time.

When you need it

Locks and leader election. Several instances of a scheduler must agree on which one runs the nightly billing job, so each tries to take a lock by creating a key in etcd or ZooKeeper. A lock that two instances can both believe they hold is worse than none, so taking it must be a linearizable compare-and-set.

Uniqueness and other hard constraints. Two sign-ups choosing the same email address, two buyers taking the last unit of stock, a balance that must never go negative: enforcing these at write time needs one up-to-date value that everyone agrees on. Constraints you can check later and repair by apologizing do not.

Information that travels by a second path. An order service writes order 4471 to the database, then puts "render the invoice for 4471" on a message queue. If the invoice worker reads from a follower that is behind, it finds no such order: the queue beat replication. Either read from a linearizable source, or carry enough in the message (the data, or a version to wait for) that the race cannot hurt.

Replication and linearizability

Single-leader replication can be linearizable if reads go to the leader or to synchronously updated followers, and if the leader really is the leader. Asynchronous failover can promote a follower that lacks acknowledged writes, and a deposed leader that has not noticed may keep answering.

Consensus algorithms such as Raft and Zab are built to prevent split brain and stale replicas, which is how etcd and ZooKeeper offer linearizable operations. Details still matter: ZooKeeper reads may lag unless the client calls sync first, while etcd reads are linearizable by default.

Multi-leader replication is not linearizable: several nodes accept writes at once and replicate them later.

Leaderless replication is probably not. Last write wins with wall clocks cannot be, because of clock skew, and sloppy quorums give it up entirely. Even strict quorums (w + r > n) can produce the flip-back history: while a write is spreading, one reader's quorum includes a replica with the new value and a later reader's does not. Synchronous read repair fixes reads and writes at a cost in latency, but not compare-and-set, which needs consensus.

The cost: CAP and latency

Suppose a database runs in two data centres and the link between them fails while both keep serving local clients. To stay linearizable, the side that cannot reach the leader must refuse requests. If both sides keep answering from their own copy, the copies drift apart and the system is no longer linearizable. There is no third option.

That trade-off is the content of the CAP theorem. It is often quoted as "consistency, availability, partition tolerance: pick two", which misleads. A network partition is not something you choose; it happens to you. The accurate version is: when the network is partitioned, you must choose between linearizability and availability. When the network works, you can have both. The C in CAP means linearizability specifically, and the A means that every node that has not failed answers every request, a stricter bar than most operators use.CAP covers one consistency model and one kind of fault. It says nothing about slow links, crashed nodes, or weaker models, which limits how much it helps with real designs.

The more common reason to give up linearizability is speed. Even with no faults, a linearizable operation must coordinate with other nodes, so its response time is tied to network delay, and with the unpredictable delays of Chapter 8 that means slow tails. It has been proven that any linearizable register has response times at least proportional to the uncertainty in network delay; weaker models can answer from local state. Even the RAM of a multi-core CPU is not linearizable without memory barriers, for the same reason: speed, not fault tolerance.

In practice, keep linearizability for the few decisions that must be unique and immediate, such as locks, leases, and claims, and let the bulk of the data use something cheaper.
