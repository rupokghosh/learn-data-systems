Beyond MapReduce

MapReduce proved that ordinary programmers could process petabytes on unreliable hardware. It also turned out to be a clumsy way to express most real jobs, and a slow way to run them. The systems that replaced it, Apache Spark, Apache Tez, and Apache Flink among them, kept the important ideas: partitioning by key, deterministic tasks, and recovery by re-execution. What they changed was how a multi-step workflow is planned and where its intermediate data lives.

The cost of writing every step down

In a chain of MapReduce jobs, the output of every job is written to the distributed filesystem before the next one starts. That output is called intermediate state: no one wants it for its own sake, it only exists to pass data from one job to the next. Making it a real file has three costs. Each byte is replicated to several machines, so it crosses the network and hits disk several times over. A job cannot begin until every task of the job before it has finished, so a single straggler stalls the whole chain. And the next job often begins with a mapper that does nothing but read the file back and pass records through to a shuffle.

The upside is real too. A file is easy to inspect when something goes wrong, and if a later job fails, it can restart from the last file without redoing anything earlier. The Unix pipe makes the opposite choice: it streams data between processes through a small buffer and writes nothing down.

Dataflow engines

A dataflow engine treats the whole workflow as one job, a graph of operators. An operator is a function like a mapper or a reducer, but the engine is free to connect operators in more ways than map-then-reduce: repartition and sort by key, repartition without sorting when only grouping is needed, broadcast one input to every task, or simply pass records along to the next operator on the same machine. Sorting happens only where an operator actually needs it.

Because the engine sees the whole graph, it can keep intermediate data in memory or spill it to local disk without replication, schedule each task near its input, start an operator as soon as its input is ready, and reuse worker processes rather than starting a fresh JVM for every task. A shuffle is still a barrier, since a sort cannot emit its first record until it has seen its last input, but steps that need no shuffle run as a pipeline.

Fault tolerance from lineage

Without durable intermediate files, a dataflow engine needs another way to recover from a lost machine. Spark tracks the lineage of every partition of data: which input it was computed from and which operators were applied. When a partition is lost, Spark recomputes just that partition from the closest ancestor that still exists, which may be the original input. Flink takes a different route and periodically checkpoints operator state, so it can roll back to a recent consistent point.

Recomputation is only safe if it reproduces the same data. If an operator depends on iteration order of a hash table, a random number, or the current time, a recomputed partition may differ from the lost one, and every downstream partition that consumed the old version is now inconsistent and has to be recomputed as well. Engines therefore push operators to be deterministic, and the reliable fix is to seed randomness and avoid reading clocks inside a job. When recomputing a partition would be expensive, for example because the intermediate data is much smaller than the input it came from, it is cheaper to write that intermediate result down after all. Graphs and iterative processing

Some algorithms are naturally iterative: PageRank, shortest paths, connected components, and many machine learning methods repeat a step until the result stops changing. Expressed as MapReduce, each iteration is a full job that reads the entire graph and writes it out again, even when only a few vertices changed.

The bulk synchronous parallel model, made popular by Google's Pregel paper and implemented by Apache Giraph, Spark GraphX, and Flink's Gelly, does better. Each vertex has a value and runs a small function. In each round, called a superstep, a vertex reads the messages sent to it in the previous superstep, updates its value, and sends messages along its edges. Vertex state stays in memory between supersteps, and a vertex that receives no messages does no work. The computation ends when no messages are sent.

Count how many messages cross between workers. Vertices are usually assigned to workers by hashing their ID, so neighbors rarely share a machine, and most messages go over the network. Every superstep also ends with a barrier where all workers wait for the slowest. Fault tolerance comes from checkpointing all vertex state at the end of a superstep and rolling everything back to the checkpoint if a worker dies. For graphs that fit in the memory of one large machine, a single-threaded program often beats a distributed graph engine for exactly these reasons.

High-level APIs and declarative queries

Writing raw map and reduce functions was laborious, so higher-level tools appeared almost at once: Hive put SQL on top of MapReduce, and Pig offered a scripting language of relational operations. Today the same idea appears as Spark SQL and DataFrames, Flink's Table API, and engines such as Trino. You describe joins, filters, and aggregations, and the engine turns them into a dataflow graph.

The declarative part matters more than the convenience. When the engine knows that an operation is a join rather than an arbitrary function, a query optimizer can choose the join algorithm from the previous lesson by itself: broadcast the small table, or shuffle both sides, based on table statistics. Knowing which columns a query uses lets it read only those columns from a columnar format such as Parquet, and knowing the types lets it generate compact, vectorized code instead of calling a function per record. Batch engines borrowed these techniques from analytic databases, and the two families have largely converged. The difference that remains is flexibility: a batch engine still lets you drop into arbitrary code for the steps that SQL cannot express, such as training a model or parsing an unusual file format.
