Faults and unreliable networks

A program running on one computer fails in a tidy way. If the memory is corrupted or a disk controller misbehaves, the usual result is a crash, not a slightly wrong answer. Hardware and operating systems are designed like this on purpose: it is easier to reason about a machine that either works or stops than about one that works a little.

Spread the same program across several machines and that tidiness is gone. Some parts keep working while others are broken, and the broken parts do not announce themselves. This lesson is about the network, the first and most stubborn source of that uncertainty.

Partial failure

In a distributed system, a partial failure is the normal state of affairs: one node is overloaded, one link drops packets, one disk is slow, and everything else is fine. Worse, these failures are nondeterministic. The same request may succeed, fail, or do something in between, and you may not be able to find out which.

Not every large system treats this the same way. A supercomputer running a weather simulation for a week typically checkpoints its state, and when a node dies it stops the whole job and restarts from the last checkpoint. That turns a partial failure back into a total one, which is acceptable for batch work. An online service cannot do that. It runs on commodity machines in shared datacentres, it must stay available while machines are replaced and software is upgraded one node at a time, and its users are spread across continents. Such a system has to tolerate partial failure in software, because there will always be something broken somewhere.

What the sender cannot know

Most datacentre networks, and the internet, are asynchronous packet networks. A node can send a packet to another, but the network promises neither when it will arrive nor that it will arrive at all. When you send a request and wait for an answer, many different things can go wrong, and from the sender's side they all look the same.

What the client heard before giving up never changes. Whatever happened, the client knows only that it has no answer yet. In four of the six cases the server did the work anyway, so a blind retry of something like "charge this card" can run twice.TCP does not close this gap. A TCP acknowledgement means the remote kernel received the bytes, not that the application processed them before it crashed. This is why idempotent operations and request IDs show up all over distributed systems.

Network faults are not rare in practice. Operators of large datacentres report regular trouble from misconfigured or rebooting switches, links that fail in only one direction, and whole racks cut off when their top-of-rack switch dies. When part of the network is cut off from the rest, that is a network partition. You do not have to make the network perfect, but you do need to know what your software does when it misbehaves, and the honest way to find out is to break it on purpose in testing.

Sometimes there is direct feedback. If the machine is up but no process listens on the port, the operating system answers with a reset. A router that knows a host is unreachable may say so. A process that crashes while its machine survives can have a supervisor tell the rest of the cluster. But none of these cover a frozen process, a dead machine, or a silent link, so in the end every system relies on a timeout.

Where the delay comes from

If the network had a known maximum delay d and the server always answered within r, a timeout of 2d + r would be exact. Real networks give no such bound. Most of the variable delay is time spent waiting in queues:

  • Switch queues. When several machines send to the same destination at once, their packets wait for the one output link. If the queue fills, packets are dropped.
  • Operating system queues. A packet that has arrived waits until the application thread gets a CPU core.
  • Virtualization. A virtual machine can be paused for tens of milliseconds while the hypervisor runs another tenant, and incoming data is buffered in the meantime.
  • TCP itself. Flow control slows a sender down to protect the receiver and the network, and lost packets are retried only after a timeout, so loss shows up as delay.

In a public cloud you share all of these with strangers. A neighbour running a large shuffle in Spark can fill the switch you depend on, and you will see it only as unexplained latency. This is also why latency-sensitive traffic such as voice calls often uses UDP: a packet that arrives too late is useless, so it is better not to retransmit it at all.

Choosing a timeout

A short timeout notices a dead node quickly but sometimes declares a healthy, merely slow node dead. A long timeout avoids false alarms but leaves requests waiting on a node that is gone. A false alarm is not free: the cluster moves the node's work elsewhere, which adds load to nodes that may already be struggling, and an action that was in progress may run a second time. There is no correct value to look up. The practical approach is to measure the distribution of round-trip times on your own network, over days rather than minutes, and pick a timeout from its tail. Better still, let the system adjust as conditions change. A phi accrual failure detector, used by Akka and Cassandra, does this: instead of a yes or no verdict, it keeps a running estimate of how heartbeat intervals are distributed and reports a suspicion level that rises the longer a heartbeat is overdue.Each component can then pick its own threshold on the same suspicion value, trading speed against false alarms independently.

Circuits versus packets

Telephone networks once showed that bounded delay is possible. A call sets up a circuit: a fixed share of bandwidth reserved along the whole route for as long as the call lasts. Nobody else can use that share, so there is nothing to queue behind, and the end-to-end delay has a known upper limit. Such a network is synchronous in the technical sense.

Datacentre networks chose differently, and for good reason. Data transfers are bursty: a file copy wants all the bandwidth it can get for a few seconds, then nothing. Reserving a fixed slice per connection would either waste capacity or make transfers slow. Packet switching lets every connection share whatever bandwidth is free right now, which uses the hardware far better, at the price of queues and therefore unbounded delay. Quality of service features and admission control can narrow the variation, but multi-tenant clouds do not offer them to you. Unbounded delay is the cost of cheap, high utilization, and your timeouts have to live with it.
