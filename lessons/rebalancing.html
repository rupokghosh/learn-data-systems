Rebalancing partitions

A cluster does not stand still. Data grows, so you add disks and machines. Traffic grows, so you add CPUs. A machine dies, and its share of the work has to go somewhere. Each of these changes means moving data and requests from some nodes to others, a process called rebalancing.

Whatever the strategy, three things should hold. Afterwards, load should again be spread fairly. While it runs, the database should keep serving reads and writes. And it should move no more data than necessary, because every byte copied competes with real traffic for network and disk.

Why not hash mod N

With hash partitioning, the obvious rule is to send a key to node hash(key) mod N, where N is the number of nodes. It spreads keys evenly and needs no lookup table. The trouble starts when N changes. A key whose hash is 1,000,003 lives on node 3 of a ten-node cluster. Add an eleventh node and it belongs on node 4; with twelve nodes, on node 7. Almost every key changes node every time the cluster changes size, so adding one machine to relieve pressure sets off a near-total reshuffle of the data, at exactly the moment the cluster is short of capacity.

A fixed number of partitions

The fix is to stop tying partitions to nodes. Create many more partitions than there are nodes, for example 1,000 partitions on a ten-node cluster, about a hundred each. A key's partition never changes, because the number of partitions never changes. When a node joins, it takes a few whole partitions from each existing node until the shares even out. When a node leaves, its partitions are dealt out to the others. Only the mapping from partitions to nodes changes, and only the partitions that move are copied. The old owner keeps serving a partition while the copy is in transit and hands it over once the new node has caught up.

Riak, Couchbase, and Elasticsearch all rebalance this way. Elasticsearch fixes the number of primary shards when an index is created; changing it later means splitting or shrinking the index, or reindexing it. The partition count therefore has to be chosen up front with room for growth. Too few, and each partition becomes so large that moving or recovering it takes hours. Too many, and the fixed overhead of each one, its files, memory, and bookkeeping, adds up. Machines of different sizes are easy to accommodate: a bigger node simply gets more partitions.A common rule of thumb for Elasticsearch is to keep shards in the tens of gigabytes; Kafka users choose partition counts with the largest consumer group they expect in mind.

Dynamic partitions and the hash ring

Fixed partitions fit hash partitioning well and key ranges badly. If range boundaries are chosen poorly, some partitions sit nearly empty while others overflow. Databases that partition by key range, such as HBase and MongoDB with ranged sharding, therefore create partitions dynamically. When a partition grows past a configured size, ten gigabytes by default for an HBase region, it is split at its middle key, and one half can move to another node. When deletions shrink it, it can be merged with a neighbour. The number of partitions follows the volume of data. One catch: an empty database starts with a single partition, so every write goes to one node until the first split. Both HBase and MongoDB let you pre-split a new table into ranges you choose when you know roughly what the keys will look like.

A third approach ties the number of partitions to the number of nodes. In Cassandra each node owns a fixed number of tokens, points on the range of hash values; 16 by default since Cassandra 4.0, and 256 before that. Each token owns the stretch of hash values just before it. A new node picks its own tokens at random and takes over the stretches in front of them, so it relieves many existing nodes a little each. Random points only balance out on average, which is why each node gets many tokens rather than one.

Drawn on a circle, with each key owned by the next token clockwise, this is usually called consistent hashing. The name is used loosely. It comes from a 1997 paper about spreading load across web caches without central coordination, and many systems that use the phrase really mean hash partitioning with randomly chosen boundaries. When in doubt, ask what is being hashed and who decides the boundaries.

Going from N to N + 1 nodes, hash mod N moves about N/(N + 1) of the keys: four-fifths of the data when a fifth node joins. Fixed partitions and the ring move about 1/(N + 1), which is the least any scheme can do, since the new node has to end up with its share and every moved key goes to it. Fixed partitions land slightly off the ideal because whole partitions move, not single keys. Try the ring with one token per node: moves are still minimal, but the arcs are so uneven that one node can carry many times another's load.

Automatic or manual

Should the cluster rebalance itself? Fully automatic rebalancing is convenient, but moving partitions is expensive. It consumes network bandwidth and disk throughput and slows the very requests the cluster exists to serve. Combined with automatic failure detection it can be dangerous. Suppose one node is overloaded and slow to answer health checks. The cluster declares it dead and starts moving its partitions elsewhere, which adds load to the receiving nodes and to the struggling node that has to send the data. Now a second node is slow, and the cascade continues.

Many systems therefore keep a human in the loop or put brakes on the machinery. Kafka never moves partitions between brokers on its own: an operator, or a tool such as Cruise Control, produces a reassignment plan and runs it with a bandwidth throttle. MongoDB's balancer can be limited to a nightly window. Elasticsearch operators routinely disable shard allocation during a rolling restart, so that a node that is away for two minutes does not trigger a mass copy of everything it held. Automation is good at the arithmetic; a person is often better at telling a dead node from a busy one.
