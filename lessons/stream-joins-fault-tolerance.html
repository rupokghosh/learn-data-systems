Stream joins and fault tolerance

Joins in a batch job are comfortable: both inputs are complete, so you can sort them, hash them, and match every record with every partner. A stream processor has no such luxury. New data can arrive on either side at any moment, which means the processor must keep state about what it has already seen in order to match it with what comes next. That state is also what makes recovering from a crash hard. This lesson covers the three kinds of stream join and then how a processor can crash, restart, and still produce each output exactly once in effect.

Stream-table joins: enrichment

The most common join adds context to each event. A coffee chain's purchase events carry only a member ID, and the loyalty service needs the member's tier to apply the right discount. Querying the members database for every purchase would work, but it is slow and can overload the database. Instead, the stream processor keeps a local copy of the table, in memory or in an embedded store such as RocksDB, and keeps it current by consuming the table's change stream through change data capture. The join then becomes a local lookup.

Now the processor reads two streams, purchases and table changes, and the order in which they reach it is not the order in which things happened. If a member is upgraded to gold a second before buying a coffee, but the change stream is running a few seconds behind, the purchase meets the old tier.

The latest-table join is fast and usually right, but its answer depends on timing, so rerunning the same input can produce different output. Data warehouses call this problem slowly changing dimensions, and the fix is the same in both worlds: give each version of a row its own identifier or validity interval, and join each event with the version that was valid at its event time. In a stream processor that means keeping table history and holding events until the change stream is known to have passed their timestamp. You trade latency and memory for determinism.

Stream-stream joins: matching within a window

Sometimes both sides are event streams. A news app sends push notifications and wants to know which app opens they caused. An open counts for a notification only if it happens within some window after the send. To join them, the processor indexes recent notifications by ID, and when an open arrives, it looks for the matching notification. When a notification's window expires without an open, the processor can emit a "notification ignored" event, which is often the more interesting result.

The window size is a business decision with an engineering cost. It sets how much state the processor must hold, which in production is per user and per notification, so a window ten times longer means roughly ten times the state. It also sets how long you wait before you can say anything happened: "no open" is only known once the window closes.

Table-table joins: maintaining a view

When both inputs are change streams of tables, the output is itself a table: a materialized view of the join, kept current. Picture a podcast app that shows each listener a queue of new episodes from the shows they follow. One input is the change stream of the follows table, the other the change stream of the episodes table. The processor keeps both tables locally and applies a rule for each kind of change:

new episode of show S      → add it to the queue of every follower of S
listener L follows show S  → add S's recent episodes to L's queue
listener L unfollows S     → remove S's episodes from L's queue
episode deleted            → remove it from every queue

This is the same calculation as a SQL join of the two tables, but performed incrementally: each input change produces exactly the changes to the result that it implies. Kafka Streams expresses this directly as a join between two KTables. As with the other joins, if the two change streams are not ordered with respect to each other, the result for a given moment depends on which change arrived first.

Fault tolerance and exactly-once effects

A batch job that fails can simply be rerun, because its input is fixed and its output is only published when the job succeeds. A stream never finishes, so you cannot wait for the end before making output visible. Stream processors use two related tricks to get a similar guarantee. Microbatching, as in Spark Streaming, cuts the stream into small batches of about a second and treats each as a tiny batch job. Checkpointing, as in Apache Flink, periodically writes a consistent snapshot of all operator state to durable storage, coordinated by barrier markers that flow through the stream; after a crash, everything restarts from the last checkpoint.

Both guarantee that the processor's internal state reflects each input exactly once. Neither can unsend an email or take back a row written to an external database before the crash. The figure shows the problem with a consumer that credits loyalty points for each message: it writes the output and records progress by committing its offset, and a crash can land between the two.

Committing first loses messages; writing first duplicates them. There are two ways out. The first is atomic commit: make the output and the offset part of one transaction, so that either both become visible or neither does. Kafka transactions do this when the output is another Kafka topic, and you can do it yourself when the output is a relational database by storing the consumer's offsets in a table of that same database. The second is idempotence: make repeating a write harmless. Store the message's offset with the row and upsert on it, or keep the offset of the last applied message per key and skip anything older.Idempotence has preconditions: messages must be replayed in the same order, processing must be deterministic, and no other writer may update the same rows concurrently. A zombie instance that was declared dead but is still running needs fencing.

Finally, state must survive the crash too. A processor that keeps a local table or window contents can write them to a remote store, which is slow; replicate them as a changelog topic, as Kafka Streams does; or snapshot them with each checkpoint, as Flink does to HDFS or S3. For small windows it is sometimes cheapest to rebuild state by replaying the last few minutes of input. Which to pick depends on how large the state is, how fast you need to recover, and whether your network or your disks are the scarcer resource.
