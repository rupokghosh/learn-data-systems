Leaderless replication and quorums

Both designs so far funnel each write through a leader that decides the order of changes. A third family drops the leader entirely: any replica accepts writes, and the client, or a coordinator node acting for it, sends each write to several replicas directly. Amazon described this approach in its 2007 Dynamo paper, and Riak, Cassandra, and Voldemort followed it, which is why it is often called Dynamo-style replication.Amazon's later DynamoDB service shares the name but, internally, uses leader-based replication per partition.

Without a leader there is no failover. If a replica is down, the write still goes to the others. The cost is that the replicas can disagree, and the system needs ways to notice and repair that.

Writing to several replicas

Each key is stored on n replicas. A write goes to all of them and counts as successful once w of them acknowledge it. A replica that was down at the time simply misses the write, and when it comes back it is stale. So reads also go to several replicas, and every value carries a version number; the client takes the newest version among the answers.

Two mechanisms bring stale replicas back up to date:

  • Read repair. When a read collects answers and notices that some replica returned an older version, the client writes the newer version back to it. Values that are read often get repaired quickly.
  • Anti-entropy. A background process compares replicas and copies whatever is missing. It does not preserve any write order and may run slowly, but without it, values that are rarely read could stay stale on some replicas indefinitely. Cassandra and Riak compare replicas efficiently with Merkle trees, hashes over ranges of keys.

Quorums: w + r > n

If a write is acknowledged by w replicas, and a read waits for answers from r replicas, then as long as w + r > n the two groups must overlap: there are not enough replicas for them to be disjoint. At least one replica the read hears from has the latest successful write. Reads and writes that obey this rule are called quorum reads and writes.

A common choice is an odd n, such as 3 or 5, with w = r = (n + 1) / 2. With n = 3, w = r = 2, one replica can be down and both reads and writes still work; with n = 5, w = r = 3, two can be. You can also skew it: w = n, r = 1 makes reads fast and cheap, at the price that a single failed replica blocks every write. Cassandra exposes the choice per query, as consistency levels such as ONE, QUORUM, and ALL.

Try a sequence in the playground. With the defaults, fail R1, write, recover R1, and read a few times. Every read hears from at least one replica holding the newest version, and when R1 answers with an old one, read repair fixes it. Then set w and r to 1 and press Read right after Write: some reads now come back stale with no failure at all, because the one replica that answers first may not have received the write yet.

What a quorum does not promise

The overlap argument is tidy, but it rests on assumptions that real systems break regularly. Even with w + r > n, a read can return an old value when:

  • A sloppy quorum is in use (below): the w acknowledgements may come from nodes outside the n that reads consult.
  • Two writes are concurrent. The replicas may apply them in different orders, and if the system settles that by keeping the higher timestamp, one write disappears. The next lesson is about this case.
  • A read overlaps a write. While a write is still in progress, some replicas have the new value and some do not, and a read may or may not see it.
  • A write fails partway. If fewer than w replicas acknowledge, the client is told the write failed, yet the replicas that did store it keep it. You can see this in the playground: fail two of three replicas with w = 2 and write.
  • A replica is restored from an old copy. If a replica holding the newest value dies and is rebuilt from one with an older value, fewer than w replicas may now hold the newest one.

So quorums make stale reads unlikely, not impossible. They are a tuning knob for probability and latency, not a guarantee in the sense of the stronger consistency models later in the book. Monitoring is harder too: a leader-based system can report how far each follower is behind in its log, but leaderless replicas share no log, so there is no simple lag number to alert on.

Sloppy quorums and hinted handoff

Now suppose a network problem cuts a client off from most of the n replicas for some key, while other nodes in the cluster remain reachable. The system can return errors for writes it cannot place on w of the key's home replicas, or it can accept them on any w reachable nodes, including ones that do not normally hold the key. The second option is a sloppy quorum. When the home replicas become reachable again, the stand-ins send them what they held, which is called hinted handoff.

Turn on Sloppy quorum in the playground, fail two replicas, and write. Stand-ins S1 and S2 accept the write on behalf of the failed ones, so it succeeds. Now recover the replicas, fail the third, and read straight away: the newest value may still be on its way, so the read can come back stale even though w + r > n. A sloppy quorum improves write availability by giving up the overlap guarantee until handoff completes. It is an option in the common Dynamo-style databases: Riak has it on by default, while Cassandra and Voldemort ship with it off.
