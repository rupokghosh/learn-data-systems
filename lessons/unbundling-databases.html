Unbundling databases

Unix and the relational database both set out to help people manage data, and they took opposite routes. Unix gives you small, sharp tools and a thin, low-level abstraction, the stream of bytes, to connect them with pipes. A relational database gives you one large tool and a high-level abstraction, the declarative query, behind which the system chooses indexes, join algorithms, and replication without your involvement. One trusts the programmer to compose; the other hides the composition. Much of modern data infrastructure is an attempt to get the strengths of both.

A database is already a dataflow system

Look inside a database and you find derived data everywhere. Running CREATE INDEX makes the database scan the table, build a sorted copy of one column with pointers back to rows, and then keep that copy up to date on every write. A materialized view is a stored query result maintained the same way. A follower replica is a copy built by replaying the leader's log. A full-text index in PostgreSQL or Elasticsearch is a derived inverted index. Each is a function from the primary data to another shape, and the database runs the dataflow for you, transactionally.

The catch is that the dataflow stops at the database's edge. If your search lives in Elasticsearch and your analytics in a warehouse, the database cannot maintain them. Two broad answers have emerged:

A federated database, or polystore, offers one query interface over many storage engines: PostgreSQL's foreign data wrappers and engines such as Trino let a single SQL query join a table with a file in object storage. That unifies reads, but it does nothing to keep the stores consistent with each other when data changes. An unbundled design unifies writes instead: changes flow through an ordered log, and each store subscribes and maintains its own derived view. That is the database's internal index maintenance, pulled apart and spread across a data centre, with Kafka playing the role of the replication log and each consumer playing the role of an index.

Unbundling is not a reason to replace a database that already does what you need. A single PostgreSQL instance with good indexes beats a fleet of specialized systems on simplicity, and simplicity is worth a lot. The goal is breadth: when no single product covers your workloads, you can compose several without falling back on fragile dual writes. The composition is where the complexity lives, so it should be as boring and as well-tested as possibleThe log consumers need the same care as any database component: idempotent apply, monitoring of lag, and a tested path for rebuilding from scratch..

Application code as a derivation function

Once you think in derived datasets, a lot of application code turns out to be a function from one dataset to another. A machine learning feature pipeline, a search indexer that lowercases and stems words, a job that turns order events into a stock-level table: each takes input data and produces derived data. Databases are good at a narrow set of such functions (indexes, views, triggers) and bad at running arbitrary code with its own dependencies and deployment cycle. Stream processors such as Flink and Kafka Streams fill that gap: they run your code as the derivation function, with the log as input and a store as output.

This suggests keeping application code stateless and putting state in purpose-built stores, a split web applications already practise. The usual arrangement is still request and response: the code asks the database a question and waits. The dataflow alternative inverts it. Suppose a food delivery service quotes an arrival time on every order, and the quote depends on each kitchen's current preparation time. Instead of calling the kitchen service synchronously for every quote, the ordering service subscribes to the stream of preparation-time changes and keeps a local table. Quoting then becomes a local lookup, faster and unaffected when the kitchen service is down, at the price of a figure that may be a few seconds old. The time dependence becomes explicit, too: the order can record which version of the preparation time it used.

Moving the boundary between writes and reads

Every derived view divides work into two halves. The write path is the precomputation that happens eagerly when data comes in. The read path is the work that happens lazily when someone asks. Indexes, caches, and materialized views are all ways to move that boundary: they shift work from read time to write time, and pay for it in write amplification, storage, and the delay before a write becomes visible.

Consider a "trending near you" panel in a second-hand marketplace: listings ranked by how many people saved them, within a few blocks of the viewer. The figure runs a simulated two-minute workload of 3,000 listings, 1,200 users, and ten saves per second against five designs and counts the records each one touches.

No position is right in general. With few readers, scanning or a good index is cheapest and always fresh. As reads grow, moving the ranking to the write path wins by orders of magnitude, and a stream processor can keep each area's top list current within half a second. A time-based cache sits awkwardly in between: cheap to add, but its staleness is chosen by a timer rather than by how quickly changes actually propagate. The search index, the cache, and the materialized view are the same idea at different points on one line.

Pushing state to clients, and reads as events

The write path traditionally stops at the server: the browser fetches a page, and the data on it goes stale the moment it renders. Mobile apps that work offline already break this, holding a local copy of state and syncing later. Push protocols such as WebSockets and server-sent events let the server send each change as it happens, so the client becomes one more subscriber to the log, and the end of the write path is the user's screen. Reactive front-end state libraries and replicated client-side databases follow the same model. A client that disconnects can resume from its last seen offset, the way a Kafka consumer does.

Taken further, reads can be events too. If a read request is written to a stream and joined with the derived state by a stream processor, the system records who saw what, and when. That is useful for causality ("the buyer saw price 42 before buying") and for multi-partition queries routed through the same infrastructure as writes. It costs storage and latency, so it fits where the record of reads matters, not everywhere.
