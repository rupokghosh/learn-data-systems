Request routing

Once data is spread over many machines, a client that wants the value for cart:nia has to find the one machine that holds it. The answer is a moving target: partitions migrate when nodes join, leave, or fill up, so yesterday's address for a key may be wrong today. Every partitioned database has to solve this lookup, and it has to solve it on every single request.This is a special case of service discovery. Finding the machines themselves, their IP addresses, changes rarely and is usually left to DNS. Finding which machine holds which partition changes far more often.

Three places to put the map

The knowledge of which partition lives where can sit in one of three places.

Any node forwards. Clients connect to any node, perhaps through a round-robin load balancer. If that node owns the partition, it answers. If not, it forwards the request to the node that does, waits, and relays the reply. Cassandra works like this: whichever node receives a request acts as its coordinator. Elasticsearch does the same, with every node able to coordinate a search.

A routing tier. Every request goes to a layer of processes that store no data and exist only to forward requests to the right node. MongoDB's mongos processes play this role, and so do Vitess's VTGate servers in front of sharded MySQL.

Partition-aware clients. The client library keeps the map itself and connects straight to the owner. Kafka producers fetch metadata about which broker leads each partition and then send to that broker directly. Redis Cluster clients cache a map from hash slots to nodes and fix it whenever a node tells them they guessed wrong.

Moving the knowledge closer to the client removes hops, two per request when a routing tier disappears, but puts more machinery into every client library, in every language your organisation uses.

Who keeps the map

In all three styles somebody must know the current assignment, and the participants must agree on it, or requests go astray. Getting distributed machines to agree is a hard problem in its own right, so many systems hand it to a coordination service such as ZooKeeper or etcd. Each node registers the partitions it holds. The coordination service keeps the authoritative map, and routing tiers or clients subscribe to it, which ZooKeeper calls setting a watch, so they are notified the moment it changes.

HBase and SolrCloud keep partition assignments in ZooKeeper. Kafka did too for many years and now keeps the same metadata in its own Raft-based controller quorum, called KRaft. MongoDB uses its config servers, a dedicated replica set, rather than ZooKeeper. Cassandra and Riak skip the external service and spread changes between nodes with a gossip protocol. That removes a dependency but puts more logic into every database node, and a change reaches the cluster gradually rather than all at once.

The stale-routing window

Notification is not instant. Between the moment a partition changes hands and the moment every router has heard about it, some requests are routed by the old map and reach a node that no longer owns the data. That node must not answer from whatever it has left. It either forwards the request to the new owner or replies with a redirect so the requester can retry. Redis Cluster answers with a MOVED error carrying the new address. In MongoDB, each request from mongos carries the version of the routing table it used; a shard that sees an outdated version rejects it, and mongos refreshes its table and retries.

The handover itself needs care too. While a partition is copied, the old owner keeps serving it, and writes that arrive during the copy are shipped to the new owner before the switch. Only then does the old owner stop accepting requests for that partition and start redirecting. A request already on its way to the old owner at that moment is redirected, not lost.

Try each style with the default settings. With a routing tier, the request sent during the move goes to node B by the old map, gets a redirect, and costs two extra hops. With partition-aware clients, the same thing happens inside the client. With any-node forwarding there is no ZooKeeper at all: node A hears about the move only when gossip reaches it, and until then it forwards to the old owner, which passes the request along. Raise the notification delay to widen the window, or turn off the request during the move and send your own.

Parallel query execution

Everything so far concerns reads and writes of a single key, which is what most partitioned key-value and document stores are built for. Analytic databases go much further. In a massively parallel processing (MPP) database such as Teradata, Amazon Redshift, or Snowflake, or in query engines such as Trino and Spark SQL, the optimizer breaks one query with joins, filters, and aggregations into stages. Each stage runs on many nodes at once, and intermediate results are repartitioned between nodes as the query proceeds. Routing there is no longer about finding one node, but about planning how data flows between all of them, which is the subject of the chapter on batch processing.
