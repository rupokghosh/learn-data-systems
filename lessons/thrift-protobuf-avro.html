Thrift, Protocol Buffers, and Avro

The binary JSON variants in the previous lesson could not shrink much, because every record still had to carry its own field names. Apache Thrift (from Facebook), Protocol Buffers (from Google), and Apache Avro (from the Hadoop project) take the names out of the data entirely. Writer and reader both hold a schema that describes the record, so the bytes only need to say which field comes next, or, in Avro's case, nothing at all.

Write the schema once

You describe the record in an interface definition language and run a code generator that produces classes for Java, Go, Python, C++, and so on. Here is the bird-sighting record from the previous lesson in Thrift and in Protocol Buffers (proto2 syntax):

struct Sighting {                  message Sighting {
  1: required string observer,       required string observer = 1;
  2: optional i64 count,             optional sint64 count = 2;
  3: optional list<string> species,  repeated string species = 3;
  4: optional bool verified,         optional bool verified = 4;
}                                  }

The numbers are field tags. In the encoded bytes, a field is identified by its tag, never by its name. That has a consequence the next lesson depends on: you can rename a field in the schema whenever you like, but a tag, once used, means that field forever.

Four encodings of one record

The same record, encoded by real implementations of each format's rules. Edit the values and watch the byte counts. Hover a byte to see whether it is a type, a tag, a length, or part of a value.

Thrift's BinaryProtocol is the straightforward one: each field starts with a type byte and a 2-byte tag, strings carry a 4-byte length, and an i64 always takes 8 bytes, even when it holds 37. It is simple and fast to parse, and it is the biggest of the four.

CompactProtocol and Protocol Buffers pack more into less. The tag and the type share one byte: Thrift Compact stores the difference from the previous tag in the high four bits (clear the count and watch the species header change from delta 1 to delta 2), while Protocol Buffers stores (tag << 3) | wire_type. Integers and lengths become varints, which use as many bytes as the number needs. A Thrift Compact boolean disappears into its field header altogether.

Signed numbers need one more trick. A varint of a negative number in two's complement would always be huge, so these formats first apply zigzag encoding, which interleaves negatives with positives so that small magnitudes stay small.

Required, optional, and repeated

Look for required in the bytes and you will not find it. Required and optional change nothing about the encoding; they only change what the generated code checks. A required field that is missing makes parsing fail, which catches bugs early and, as the next lesson shows, makes schemas hard to change. Protocol Buffers dropped required in proto3 for that reason, and many teams using proto2 or Thrift ban it by convention.

Lists differ too. Thrift has a real list type with a header that says the element type and count. Protocol Buffers has no list type: a repeated field is simply the same tag appearing several times, which you can see as three separate keys for the three species. A nice side effect is that an optional single-valued field can later become repeated: old code reading new data sees several values and keeps the last one.

Avro: no tags at all

Avro's encoding is the smallest because it leaves out even the tags. The bytes are just the values, one after another, in the order the schema lists them: a length and some UTF-8, a union branch number and a zigzag varint, an array block. Nothing in the data says which field a value belongs to or what type it is.

record Sighting {
  string observer;
  union { null, long } count = null;
  array<string> species;
  boolean verified;
}

So a reader can only decode Avro data if it knows the exact schema the writer used, the writer's schema. It decodes with that, then translates the result into the schema its own code expects, the reader's schema. The two do not need to be identical, only compatible. Avro matches fields by name, so order does not matter. A field the writer had and the reader does not is ignored. A field the reader expects and the writer did not have is filled from the default in the reader's schema.

Where does the reader get the writer's schema? Sending it with every record would erase the size advantage, so it depends on the setting.This is also why Avro suits schemas generated by a program, for example one Avro schema per database table in an export job. With no tags to assign by hand, a changed table simply produces a new schema.

  • Large files of many records, as in Hadoop or a data lake, store the writer's schema once in the file header. Avro's object container files do exactly this.
  • Databases and logs where records were written over months by different code versions store a small schema version number with each record and keep the schemas in a registry. Kafka deployments commonly use a schema registry this way, with the id in the first bytes of each message.
  • Network connections can agree on the schema once when the connection opens and use it for the connection's lifetime.

Whichever format you use, the schema becomes valuable documentation that cannot drift from the data, and a registry of past schemas lets you check, before you deploy, whether a change will break readers. The next lesson does that check interactively.
