Unreliable clocks

Applications ask the clock two kinds of question. How long did something take: a request duration, a cache entry's age, whether a timeout has passed. And when did something happen: the time on a log line, the expiry date of a session, the moment a row was written. Each machine answers both questions with its own hardware, usually a quartz oscillator, and no two machines agree exactly.

Two kinds of clock

A time-of-day clock returns the current date and time, typically as seconds since the Unix epoch. On Linux this is clock_gettime(CLOCK_REALTIME); in Java it is System.currentTimeMillis(). It is kept close to everyone else's time by synchronizing with NTP servers, and that is exactly what makes it awkward: when the local clock has run too far ahead, synchronization can set it back, so a later reading can be smaller than an earlier one.Leap seconds cause similar trouble. A minute that lasts 61 seconds has broken real systems that assumed time only moves forward in even steps.

A monotonic clock, such as CLOCK_MONOTONIC or Java's System.nanoTime(), only ever moves forward. Its absolute value means nothing (it might count from boot), so comparing it between two machines is pointless. NTP may speed it up or slow it down slightly, by at most about 0.05 percent, but never makes it jump. Use it for every elapsed-time measurement, timeouts included.

Synchronization is rough

A quartz crystal's frequency depends on its temperature and its manufacturing, so clocks drift: commodity servers can gain or lose tens of milliseconds an hour, and a bad one does much worse. NTP corrects this by asking a server for the time, but its accuracy is limited by the network delay to that server, which, as the previous lesson showed, is not predictable. Over the internet, errors of tens of milliseconds are ordinary, and spikes during congestion can be far larger. A machine whose clock has drifted too far may refuse to synchronize or be forcibly stepped. A firewall that silently blocks NTP can leave a node drifting for weeks before anyone notices. Virtual machines add their own jitter, because a VM's notion of time stalls while it is not scheduled.

Very good accuracy is possible, with GPS receivers in every rack and the Precision Time Protocol, and trading firms do this because regulators require it. Most systems do not, so the realistic assumption is: clocks are usually close, occasionally wrong by a lot, and nothing will tell you which situation you are in.

Ordering events by timestamp

The danger is software that quietly depends on clocks being right. A common case is last write wins conflict resolution, used by Cassandra and other multi-leader and leaderless databases: every write carries a timestamp, and when two replicas disagree, the write with the larger timestamp survives. If the timestamps come from time-of-day clocks on different machines, "larger timestamp" is not the same as "later".

Two things make this dangerous. The lost write disappears silently: the database reports success to Tomas, every replica agrees, and the data is simply wrong. And synchronization does not solve it. Turn on the NTP sync and raise the drift: after a few seconds the clocks are apart again, and any two writes closer together than the current skew can be reordered. Clocks good enough for log files are not good enough to decide which of two writes was later. For that, use logical clocks, such as version numbers or version vectors, which count events instead of measuring time.

A reading is a range

It helps to think of a clock reading not as a point but as an interval. If a machine synchronized two minutes ago with a server 20 milliseconds away, and its crystal drifts at a known worst-case rate, the true time is somewhere in a window around what the clock says. Most APIs hide that window and return a single number with misleading precision.

Google's Spanner makes the window explicit. Its TrueTime API returns an earliest and a latest possible time, and Spanner uses that for snapshot isolation across datacentres. Before a transaction commits, Spanner waits until the uncertainty window of its timestamp has passed, so any transaction that starts afterwards must get a timestamp with no overlap. The wait is only cheap if the window is small, which is why Google puts GPS receivers and atomic clocks in each datacentre to keep it to a few milliseconds.

Process pauses

Clocks have one more trap, and it applies even to a monotonic clock read on a single machine. Consider a node that holds a lease: a lock with a timeout, granted by a lease service, that lets one node at a time act as leader for some piece of data. The node checks how long it has left, and if enough remains, it does the work.

deadline = granted_at + LEASE_SECONDS          # monotonic clock
while True:
    batch = inbox.take()
    if monotonic_now() > deadline - 1.0:
        deadline = renew_or_step_down()
    # checked: 2.6 s to spare. A pause can start right here.
    storage.put(plan_for(batch))

The code assumes that almost no time passes between the check and the write. Nothing guarantees that.

A thread can stop for seconds at a time for many ordinary reasons. A stop-the-world garbage collection in the JVM has been known to last minutes. A hypervisor can suspend a virtual machine to migrate it to another host. A laptop lid closes. The operating system can switch to other threads, or a noisy neighbour can steal CPU time from a VM. A memory access can trigger a page fault that waits for the disk, and in a machine short on memory, swapping can make that constant. Someone can send the process SIGSTOP by pressing Ctrl-Z. The paused thread notices none of this. When it resumes, it carries on from the next line, sure of a check it made long ago.

Systems that must answer by a deadline, such as aircraft controls, use real-time operating systems, careful memory allocation, and a great deal of testing to guarantee a response time. That is expensive and slows development, so ordinary data systems instead limit the damage. Some runtimes can warn the application that a long collection is coming, so the node stops taking requests while it runs, as if it were a short planned outage. Another approach is to allocate only short-lived objects, which are cheap to collect, and restart processes before the long-lived heap needs a full collection. Neither guarantees anything, which is why the next lesson asks how the rest of the system can protect itself from a node that wakes up with stale beliefs.
