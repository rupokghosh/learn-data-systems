Detecting concurrent writes

Leaderless and multi-leader systems let several clients write the same key at the same moment. Those writes travel over different network paths with different delays, so replicas receive them in different orders. Suppose one replica gets "set color to teal" and then "set color to amber", while another replica gets them the other way round. If each replica simply keeps the last value it received, the two disagree forever, and no amount of waiting will fix it.

To converge, every replica has to apply the same rule and reach the same result whatever the arrival order. The question is which rule, and what it costs.

Last write wins

The bluntest rule is last write wins (LWW): attach a timestamp to every write, and on every replica keep the value with the largest timestamp and discard the rest. Replicas converge, and the implementation is trivial. The price is durability. If five clients write the same key concurrently, each is told its write succeeded, and four of those writes vanish without a trace. Because the timestamps come from clocks on different machines, LWW can even discard a write that was made later and with full knowledge of the earlier one, simply because its machine's clock was behind.The multi-leader lesson shows this with a Singapore clock running 400 ms slow.

Cassandra resolves every conflict this way. LWW is reasonable when losing writes is acceptable, for example in caches or for sensor readings where the next reading replaces the last anyway. When it is not, the usual advice is to make every write go to a fresh key, such as a UUID, so values are never overwritten and nothing can be lost.

Happens-before and concurrency

To do better than LWW, a system has to tell apart two situations that look identical on the wire. Operation A happens before operation B if B knew about A: B read A's result, or depended on it, or built on it. In that case B may safely replace A. If neither knew about the other, the two are concurrent, and replacing one with the other loses information.

For any two operations there are exactly three possibilities: A happened before B, B happened before A, or they are concurrent. Concurrency here is about knowledge, not clock time. Two writes made a minute apart are concurrent if a network problem kept each writer from seeing the other's result, and two writes a millisecond apart are ordered if the second writer had already read the first.

Version numbers and siblings

A single server can track happens-before with one counter per key:

  1. The server keeps a version number for every key and increments it on every write. It stores each value together with the version that created it.
  2. A read returns every value that has not been overwritten, plus the latest version number. A client must read before it writes.
  3. A write carries the version number from the client's previous read, along with a value in which the client has merged everything it received.
  4. The server overwrites every value with that version number or lower, because the client has seen them. Values with a higher version are kept, because they were written concurrently. The values kept side by side are called siblings.

No data is silently dropped, but the work moves to the application, which has to merge siblings. For a set of items, such as a shared packing list, the union of the siblings is a natural merge. Removals break it: if one sibling no longer contains an item, the union cannot tell whether the item was removed or was simply never added. The fix is a tombstone, a marker recording that the item was removed, which the merge then subtracts.

Riak works this way and returns siblings to the application. Writing merge functions by hand is error-prone, which is why Riak also offers built-in data types, sets, counters, and maps, that merge themselves. These are conflict-free replicated data types (CRDTs), the same idea behind collaborative editing libraries such as Automerge and Yjs.

Version vectors

One counter is enough when one server assigns all the versions. With several replicas accepting writes and no leader, each replica needs its own counter, and each replica tracks the counters it has seen from all the others. That collection of counters is a version vector. Replicas send it along when they sync, and databases return it to clients with every read, so the client can send it back with its next write. Riak calls this the causal context.

Comparing two version vectors answers the happens-before question directly. If every counter in A is less than or equal to the matching counter in B, and they are not identical, A happened before B, and B's value can replace A's. If A is ahead on some counter and B on another, they are concurrent, and both values must be kept as siblings until something merges them.Version vectors are often called vector clocks. The two are closely related but not identical; Riak moved to a refinement called dotted version vectors to avoid sibling explosion.

The rules from this lesson carry over to every system that accepts writes in more than one place. If your database only offers last write wins, design for it: use immutable values under fresh keys, or accept the loss knowingly. If it offers siblings, write the merge function deliberately, decide how removals are represented, and test it with concurrent writers, not just sequential ones.
