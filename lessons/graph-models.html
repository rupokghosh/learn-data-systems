Graph-like data models

Documents handle trees well. Relational tables handle a moderate amount of linking well. But when almost anything in your data can connect to almost anything else, and the interesting questions are about the connections themselves, it is often more natural to model the data as a graph.

A graph has two kinds of things: vertices, also called nodes or entities, and edges, also called relationships. People and who follows whom, web pages and the links between them, rail stations and the tracks that join them are all classic graphs. A graph also does not need to hold only one kind of thing. A single graph can store people, places, events, and posts, with different kinds of edges between them.Facebook's TAO, for example, stores users, posts, photos, check-ins, and comments as one large graph of objects and typed associations.

Vertices, edges, and properties

The most common variant is the property graph, used by Neo4j, Memgraph, and Amazon Neptune, among others. Each vertex has a unique ID, a label saying what kind of thing it is, such as Person or City, and a set of properties as key-value pairs. Each edge has a unique ID, a tail vertex where it starts, a head vertex where it ends, a label naming the relationship, such as BORN_IN, and its own properties.

You can picture the whole model as two relational tables:

CREATE TABLE vertices (id bigint PRIMARY KEY, label text, properties jsonb);
CREATE TABLE edges (
  id         bigint PRIMARY KEY,
  tail       bigint REFERENCES vertices (id),
  head       bigint REFERENCES vertices (id),
  label      text,
  properties jsonb
);
CREATE INDEX edges_by_tail ON edges (tail);
CREATE INDEX edges_by_head ON edges (head);

Three things make this simple shape powerful. Any vertex can connect to any other, with no schema limiting which kinds may be linked. The two indexes let you find a vertex's outgoing and incoming edges quickly, so you can walk the graph in either direction. And labels let one graph hold many kinds of relationship without them getting tangled.

Geography shows why the flexibility matters. Places nest inside each other, but not uniformly. Lisbon sits inside the Lisbon District, which sits inside Portugal; Porto is recorded directly under Portugal. Some countries have states, others provinces or prefectures, and some records only know the region, not the city. A table with fixed city, region, and country columns fights that variety. A graph just adds WITHIN edges, as many as each place needs.

Pattern queries in Cypher

Cypher is the declarative query language created for Neo4j, now implemented by several other databases, and the main influence on GQL, the ISO standard graph query language published in 2024. A Cypher query draws the pattern you are looking for in ASCII art: (p:Person) is a vertex with a label, and -[:BORN_IN]-> is an edge with a direction.

Here is a question that is hard to ask of a fixed-column table: which people were born in one country and now live in a country on a different continent?

The interesting part is -[:WITHIN*0..]->: follow WITHIN edges zero or more times. Tomás was born in Campinas, two hops below Brazil. Rafael's birthplace is only recorded as the state of Minas Gerais, one hop below Brazil. Inês was born in Porto, which sits directly in Portugal. One pattern matches all of them, because it does not fix the length of the path. Try pointing someone's LIVES_IN edge straight at a country, or at a continent, and see which paths still reach a Country vertex.

As with SQL, the query says nothing about how to find the matches. The animation starts at each person and walks forward, but an engine could just as well start from the continents and walk backward along incoming edges, or begin from whichever side has fewer vertices. Those choices belong to the query planner.

The same question in SQL

Since a property graph fits in two tables, you can ask the same question in SQL. The trouble is the variable-length path. In an ordinary join you must know in advance how many joins to write, and here the number of WITHIN hops differs from place to place. Recursive common table expressions, added in SQL:1999 and supported by PostgreSQL, MySQL 8, and SQLite, exist for exactly this:

WITH RECURSIVE in_country (place, country) AS (
    SELECT id, id FROM vertices WHERE label = 'Country'
  UNION
    SELECT e.tail, ic.country
    FROM edges e JOIN in_country ic ON e.head = ic.place
    WHERE e.label = 'WITHIN'
)
SELECT person.properties->>'name' AS name
FROM vertices person
JOIN edges born    ON born.tail = person.id AND born.label = 'BORN_IN'
JOIN in_country bc ON bc.place = born.head
JOIN edges lives   ON lives.tail = person.id AND lives.label = 'LIVES_IN'
JOIN in_country lc ON lc.place = lives.head
JOIN edges c1      ON c1.tail = bc.country AND c1.label = 'WITHIN'
JOIN edges c2      ON c2.tail = lc.country AND c2.label = 'WITHIN'
WHERE c1.head <> c2.head;

The recursive part builds a lookup from every place to the country that contains it, by starting at the countries and repeatedly following WITHIN edges backward. Then the person pattern turns into six joins. It works, and PostgreSQL will run it efficiently on a modest graph. But the Cypher version is five lines that look like the diagram, and this is sixteen lines that look like plumbing. The same data can be stored either way. What differs is which questions are pleasant to ask.

Triple stores

A triple store holds the same kind of data in an even simpler shape. Every fact is a three-part statement: subject, predicate, object. The subject is a vertex. The object is either another vertex, which makes the triple an edge, or a plain value, which makes it a property. Written in the Turtle format:

@prefix : <urn:example:> .
:tomas     a :Person ;  :name "Tomás" ;            :bornIn :campinas ;  :livesIn :lisbon .
:campinas  a :City ;    :name "Campinas" ;         :within :saoPaulo .
:saoPaulo  a :Region ;  :name "São Paulo State" ;  :within :brazil .

Triple stores are usually queried with SPARQL, the query language for RDF data, implemented by systems such as Apache Jena and Amazon Neptune. Its property paths express the same variable-length walk: :bornIn/:within* means one bornIn edge followed by any number of within edges.

SELECT ?name WHERE {
  ?p :name ?name ;  :bornIn/:within* ?home ;  :livesIn/:within* ?now .
  ?home a :Country ;  :within ?c1 .
  ?now  a :Country ;  :within ?c2 .
  FILTER (?c1 != ?c2)
}

Under the different syntax it is the same idea as Cypher: describe a pattern of vertices and edges, and let the database find every place it occurs.An older relative is Datalog, which states facts and rules that may refer to themselves recursively. Datomic uses it as its query language. Tables, documents, and graphs can all store the same facts. What differs is which questions each one makes easy, and the useful skill is choosing the shape that fits the questions your application will ask most.
