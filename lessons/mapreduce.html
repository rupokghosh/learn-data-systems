MapReduce and distributed filesystems

A Unix pipeline reads files, transforms them with small programs, and writes files. MapReduce keeps that shape and spreads it over a cluster. The files live in a filesystem that spans hundreds or thousands of machines, the small programs run as many parallel tasks, and the sort in the middle of the pipeline becomes a cluster-wide sort that moves data between machines.

Google described MapReduce in 2004, and Hadoop made an open source version that defined big data infrastructure for the following decade. Few teams write raw MapReduce jobs today, but Spark, Flink, Hive, and the query engines that replaced it all inherit its model. Understanding the original makes the descendants much easier to reason about.

A filesystem spread across machines

A MapReduce job reads its input from, and writes its output to, a distributed filesystem. In Hadoop that is HDFS. Every machine in the cluster runs a DataNode daemon that stores chunks of files on its local disks. A single NameNode keeps the metadata: which blocks make up each file, and which machines hold a copy of each block.The NameNode is a single point of failure unless you run a standby with automatic failover, which typically uses ZooKeeper to decide who is active. Files are cut into large blocks, 128 MB by default, and each block is replicated to several machines, usually three, preferably in different racks.

The machines are ordinary servers with local disks, connected by a regular datacenter network; no special shared storage is involved. Hadoop 3 can replace plain replication with erasure coding, which survives the same failures with about half the extra storage. In cloud deployments the same role is often played by an object store such as Amazon S3, which trades data locality for elastic, separately billed storage.

The anatomy of a job

As a programmer you write two functions. The mapper is called once for every input record and may emit any number of key-value pairs. The reducer is called once for every distinct key, with an iterator over all the values emitted for that key. The framework does everything in between, and that in-between part is where most of the work happens.

Four things happen between the two functions you wrote. Each map task hashes the key of every pair it emits to pick a partition, one per reducer, so every pair for a given product lands at the same reducer. Before writing its output to local disk, the map task sorts each partition by key, spilling sorted runs to disk if they do not fit in memory, just like the Unix sort. When a map task finishes, each reducer fetches its partition from that task over the network. Finally each reducer merges the sorted runs it collected, which brings all the values for one key together, and calls your reducer once per key.The fetch-and-merge step is called the shuffle, a slightly unlucky name: nothing about it is random. It is a distributed sort.

Notice that partition 1 received fewer pairs than partition 2. Hashing spreads keys evenly only on average, and a key that is much more common than the others always lands in a single partition. That problem gets its own section in the lesson on joins.

Moving the code, not the data

The scheduler starts one map task per input block and tries to run it on a machine that already stores a replica of that block. A mapper's input is then read from local disk, and the only thing that crosses the network at startup is the job's code, which is a few megabytes, rather than the data, which may be terabytes. When no replica holder has a free slot, the scheduler settles for a machine in the same rack. The number of reduce tasks is not tied to the input; the job author chooses it.

The shuffle is the one phase where data must cross the network in bulk, which is why so much of the craft of writing batch jobs is about shrinking the map output. A common trick is a combiner, a mini reducer that runs on the map side: for a count, it can turn a thousand (kettle, 1) pairs into a single (kettle, 1000) before anything is sent.

Workflows of chained jobs

One MapReduce job can do one grouping. Real pipelines, such as computing which products to recommend to whom, need many, so jobs are chained: the output directory of one job becomes the input directory of the next. Unlike a Unix pipe, which streams bytes from one process to the next as they are produced, the next job in a chain can start only after every task of the previous job has finished and its output is fully written. Workflow schedulers such as Apache Oozie, Azkaban, and later Airflow manage these dependencies, and higher-level tools such as Pig, Hive, and Cascading compile a whole query into a chain of jobs for you. A workflow of fifty jobs is not unusual. The cost of all those intermediate files is the subject of the last lesson in this chapter.

Failure is a normal event

On a cluster of thousands of machines, some task fails in almost every large job: a disk dies, a machine is rebooted for a kernel patch, or a higher-priority service preempts the task's resources. MapReduce handles this simply. If a task fails, the scheduler runs it again, ideally on another machine holding a replica of the same block. The output of the failed attempt is thrown away.

That only works because of two properties. The input files are never modified, so a second attempt reads exactly what the first one read. And map and reduce functions are expected to have no side effects beyond their output, so running a task twice produces the same result as running it once. If a reducer wrote to an external database as it went, a retried attempt would write everything a second time. Output files are written to a temporary location and renamed into place only when the task succeeds, so readers never see half of an attempt.If a machine dies after its map task finished but before every reducer fetched the output, the map task has to run again too: its output lived on that machine's local disk, not in HDFS.

This design accepts doing some work twice in exchange for never having to coordinate a recovery. For a job that runs for hours on thousands of machines, that is a very good trade.
