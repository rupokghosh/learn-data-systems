Leaders and followers

Replication means keeping a copy of the same data on several machines connected by a network. You do it so the system keeps working when a machine dies, so data sits closer to the people reading it, and so read traffic can spread over more hardware. If the data never changed, replication would be a single copy job. All of the difficulty comes from change: every write has to reach every copy, and machines and networks fail halfway through that.

The most widely used answer is to put one replica in charge. PostgreSQL and MySQL streaming replication, MongoDB replica sets, and the partitions of a Kafka topic all work this way.

One leader, many followers

One replica is the leader. Clients send every write to it. The leader records the change in its own storage, then sends it to the other replicas, the followers, as an ordered stream. Each follower applies the changes in exactly the order the leader did, so it ends up with the same data. Reads may go to the leader or to any follower. Writes go only to the leader.The leader is also called the primary or master; followers are called replicas, secondaries, standbys, or read replicas, depending on the product.

The decision that matters is when the leader tells the client "saved". With synchronous replication the leader waits until a follower confirms it has the change. With asynchronous replication the leader replies as soon as its own copy is durable and ships the change in the background.

A synchronous follower is a guarantee: if the leader dies one second after replying, the write still exists on another machine. It is also a liability: when that follower is slow or down, every write waits for it. Making every follower synchronous would let any one sick machine stall the whole database, so in practice nobody does. The common compromise is semi-synchronous replication: one follower is synchronous, the rest are asynchronous, and if the synchronous one fails, an asynchronous one takes over its role. PostgreSQL expresses this with synchronous_standby_names, which names how many standbys must confirm and which ones may; MySQL's semi-synchronous mode makes the leader wait for at least one replica to confirm receipt.

Plenty of systems run fully asynchronous anyway, because then the leader never waits for anyone. The price is that a write the client was told is durable can still disappear. The simulator further down shows exactly how.

Adding a follower

You regularly need new followers: to replace a dead machine, to add read capacity, or to move to new hardware. Copying the leader's data directory is not enough, because writes keep arriving while you copy, and locking the database for the hours a large copy takes is not an option. Instead:

  1. Take a consistent snapshot of the leader without blocking writes. Most databases can already do this for backups.
  2. Record the exact position in the leader's replication log that the snapshot corresponds to. PostgreSQL calls this position the log sequence number; MySQL calls it the binlog coordinates or the GTID set.
  3. Copy the snapshot to the new machine and load it.
  4. Have the follower ask the leader for every change after that position. Once it has worked through the backlog it is caught up, and it simply keeps following the live stream.

The same request heals a follower that crashed or lost its network for a while. It knows the last position it applied, so on restart it asks the leader for everything after that and catches up. You can try it below: crash a follower, send a few writes, then restart it and watch the catch-up messages.The leader has to keep enough log around for this to work. PostgreSQL replication slots and Kafka's retention settings exist partly for this reason.

Failover

Losing a follower is easy to handle. Losing the leader is not: a follower has to be promoted, clients have to start sending writes to it, and the other followers have to start consuming from it. This is failover, and when it is automatic it usually has three steps.

  1. Decide the leader is dead. A dead machine and a slow one look the same from outside, so systems use a timeout: no answer to heartbeats for, say, 10 or 30 seconds, and the leader is presumed gone.
  2. Choose a new leader. The best candidate is the follower with the most recent data, because promoting it loses the least. Getting every node to agree on the choice is a consensus problem, which is why tools such as Patroni lean on etcd or ZooKeeper.
  3. Reconfigure. Clients must send writes to the new leader, followers must follow it, and if the old leader comes back it must accept that it is no longer in charge.

The simulator runs a leader, n1, and three followers that are progressively farther away. Two clients write: the app, which is told about any failover, and a cron job that looked up the leader's address once when it started. Every follower starts asynchronous. Send a few writes from the app, crash n1 while some are still on their way to the followers, and press Run failover. Then reset, make n2 synchronous, and do the same thing again. Finally, restart n1 after a failover and send a write from the cron job, once with fencing and once without.

Each step of failover hides a way to lose data or corrupt it.

Unreplicated writes. With asynchronous replication, the new leader may not have the last writes the old leader acknowledged. When the old leader returns, its log disagrees with the new one at the same positions, and the usual resolution is to throw its extra writes away. Clients were told those writes were durable. Worse, something outside the database may already have acted on them: an email went out, a payment was captured, or another system stored an ID that the new leader will now hand out again to a different row.

Split brain. If the old leader returns believing it still leads, and some client still talks to it, two nodes accept writes and their histories fork. The defence is fencing: every leader carries an epoch number, a node that sees a higher epoch steps down, and in harsher setups the cluster manager cuts the old leader's power or network outright. Fencing has to be designed carefully, or it can shut down both nodes.Epochs go by other names: terms in Raft and etcd, generation numbers, or leader epochs in Kafka.

The timeout. A long timeout means a long outage after a real crash. A short one triggers failovers during a load spike or a brief network hiccup, which adds work exactly when the system is already struggling, and makes split brain more likely. Because of these risks, some teams keep failover a manual decision even when their tooling can automate it.

What travels in the replication log

"Send the change to the followers" can mean several different things. The choice decides what the followers can be, how upgrades work, and who else can read the stream.

MethodWhat the leader sendsTrade-offs
Statement-basedThe SQL statement text: UPDATE stock SET qty = qty - 1 WHERE sku = 'K-17'Compact, but any statement whose result is not deterministic breaks it: NOW(), RAND(), auto-increment columns, triggers, or an UPDATE ... LIMIT without an order. MySQL switches such statements to row-based logging.
Write-ahead log shippingThe storage engine's own log: which bytes changed in which disk pagesAn exact physical copy, used by PostgreSQL streaming replication. The format is tied to the storage engine version, so leader and followers usually must run the same major version, which rules out upgrading followers first.
Logical, row-basedPer row: the new values for an insert, the key and new values for an update, the key for a deleteIndependent of the storage layout, so versions can differ. Easy for other systems to consume, which is the basis of change data capture tools such as Debezium. Used by MySQL's row-format binlog and PostgreSQL logical replication.
Trigger-basedWhatever your triggers or application code write to a change tableMost flexible: replicate a subset, transform rows, or replicate between different databases. Slower and more fragile than built-in replication.
