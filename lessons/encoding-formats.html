Formats for encoding data

Every program works with data in two shapes. While it runs, data lives in objects, structs, hash maps, and arrays, laid out for the CPU and full of pointers. The moment that data has to leave the process, to be written to a file, stored in a database column, or sent over the network, it has to become a flat sequence of bytes that makes sense without the process that produced it. The translation from the first shape to the second is called encoding (or serialization, or marshalling), and the reverse is decoding.

The choice of encoding looks like a detail, but it decides how big your messages are, how fast they are to produce and parse, which languages can read them, and, most importantly for this chapter, whether old and new versions of your code can still understand each other.

Pointers do not travel

A pointer is an address in one process's memory. Send it to another machine and it points at nothing, or at something unrelated. So an encoder has to walk the object graph and write each value out in some agreed order, with enough framing (lengths, types, markers, delimiters) for the reader to find where one value ends and the next begins.

Serialization built into the language

Most languages ship a way to dump an object to bytes with one call: java.io.Serializable in Java, pickle in Python, Marshal in Ruby. They are tempting because they handle arbitrary object graphs with no extra work. They are also a trap for anything that outlives a single process.

First, the bytes are tied to one language, and often to one version of one library, so the day a service in another language needs the data, you are stuck. Second, to rebuild the objects, the decoder has to create instances of whatever classes the bytes name. If those bytes came from outside, an attacker chooses the classes, and chains of ordinary library classes have been used to run arbitrary code during deserialization.The Python documentation says it plainly: never unpickle data you do not trust. Java deserialization flaws have produced a long list of remote code execution advisories in application servers and frameworks. Third, compatibility between versions of your own classes tends to be an afterthought, and the encodings are often slow and large. Use them for a cache that lives and dies with one deployment, if at all.

JSON, XML, and CSV

Text formats win on reach: every language can read them, and a person can read them too, which matters more than it sounds when you are debugging at 3 a.m. They also have real problems.

  • Numbers are vague. JSON has one number type and does not say whether a value is an integer, how many bits it needs, or how precise it is. XML and CSV cannot even tell a number from a string of digits without a schema.
  • No binary strings. To send an image or a hash in JSON or XML you Base64-encode it, which costs a third more space and a decoding step, and the schema has to say which strings are really bytes.
  • Schemas are optional. JSON Schema and XML Schema exist and are powerful, but many systems skip them, so the meaning of each field ends up hard-coded in every reader. CSV has no schema at all, and its escaping rules for commas, quotes, and newlines are implemented inconsistently.

The id in that record looks like the ones produced by generators that pack a timestamp, a machine number, and a sequence counter into 64 bits. The JSON text carries all nineteen digits faithfully. The damage happens in the reader: JavaScript, and many JSON libraries in other languages, store every number as an IEEE 754 double, which has only 53 significant bits. Try an id under 9007199254740992 and it comes back intact.

The usual fix is boring and effective: if a value is an identifier rather than a quantity, send it as a string. You never do arithmetic on an id, and a string cannot be rounded.

Binary variants of JSON

Inside one organization, where nobody needs to read the bytes by eye, a more compact and faster format is attractive. MessagePack, CBOR, BSON (the format MongoDB stores), and Smile all keep JSON's data model and change only the encoding: a type marker per value, integers in binary with explicit widths, and lengths in front of strings instead of quotes around them.

Look at what the inspector shows, though. The keys observer, species, and the rest are still spelled out in every single record, because without a schema the reader has no other way to know which value is which. For records with short values and descriptive names, the field names are most of the payload, and the binary variant saves only a fraction. Saving a fifth or a quarter is rarely worth giving up human readability. To do much better, the field names have to leave the data, and that requires a schema. That is the subject of the next lesson.

None of this makes JSON a bad choice. For public APIs, configuration, and data exchanged between organizations, the fact that everyone can read and write it outweighs its size and its quirks, as long as both sides agree on the awkward parts, such as how big numbers and binary data are represented.
